# Changelog

- Complete backups and timed restore drill (backlog `OPS-7`; plan `docs/superpowers/plans/2026-10-15-ops-7-restore-drill.md`, results in `docs/plans/OPS-7-RESULT.md`). Extends the dedicated-bucket `backup-job` service (`backups` profile) from Postgres-only dumps to include full incremental mirroring of the warehouse object store bucket (storing Apache Iceberg data and metadata files via `s3fs`) and ClickHouse's own state databases (change-capture offsets and ingest runs via native `BACKUP DATABASE ... TO S3(...)`). Adds `scripts/restore-from-backup.sh` to execute the full restore sequence across Postgres, the warehouse bucket, ClickHouse, and the application services, with automated empty-volume safety guards (`--force` to override). Verified via an isolated end-to-end drill (`ops7drill`) restoring 2,000 Bronze Iceberg orders, ClickHouse CDC offsets, application identities, OpenFGA permissions, and Dagster run history in 94 seconds total recovery time.
All notable changes to this project are documented in this file.

## [Unreleased]

### Added

- Oracle change capture (backlog `SRC-4`, slice 6; plan `docs/superpowers/plans/2026-10-29-src-4-databases-cdc.md`, amendments 9 to 11): a new connector type `Oracle CDC` (migration `0120`) reads the redo log through Debezium's `LogMiner` on Kafka Connect and keeps Bronze current, in the two load modes of the other change-capture types. The dial is the container database, an optional PDB name, the host and a common user; the Oracle JDBC driver is already in the pinned Kafka Connect image. "Require" means Oracle native network encryption is required (AES256, SHA256 checksum: encrypted, the server not authenticated); the verify modes are refused (`SRC-37`). The connection test asks Kafka Connect to validate the connector's configuration, so it uses the connector's own driver and encryption; a wrong login, an unreachable server and a server that refuses the encryption each have a fixed sentence. **Tables are typed by hand** as `SCHEMA.TABLE` in upper case (listing them would need an unencrypted session). **Owner-signed exception to `SEC-14` (2026-10-31):** after that test passes, the orchestrator reads Oracle's setup (`ARCHIVELOG`, minimal and all-column supplemental logging, each selected table, the session's privileges) over an **unencrypted** `python-oracledb` session, fixed data-dictionary statements only, never a table row, and the test result says so; the checks show `ok`, `missing` (with the command) or "Not checked". A failed connector says why for `ARCHIVELOG` or minimal supplemental logging off. **Limits:** no certificate checking; `ARCHIVELOG` needs a restart; Debezium only warns for a table without all-column logging, so such a table's updates arrive with unchanged columns missing (the test flags it); `LOG_MINING_FLUSH` stays in the login's schema after the connector is deleted. Proven by the new `g4-oracle` gate.

- MongoDB change capture (backlog `SRC-4`, slice 5; plan `docs/superpowers/plans/2026-10-29-src-4-databases-cdc.md`, amendment 6): a new connector type `MongoDB CDC` (migration `0119`) reads a replica set's change streams through Debezium on Kafka Connect and keeps Bronze current, in the two load modes of the other change-capture types. The dial is hosts, database, user and the replica set's name (required); there is no connection string and no `mongodb+srv`. The connector's user needs only the `read` role on its database. The connection test and the collection list run in the orchestrator. **Limits:** a replica set is required, sharded clusters are not supported; a nested document or an array stops the table's load, as in the batch connector; a MongoDB delete carries the key only; the connector takes exactly one host and always connects directly (`directConnection=true`); the console form offers no TLS choice yet (the connector takes `require`). The connection test also lists three fixed-sentence setup checks (replica set name, primary, change-stream privilege), each `ok`, `missing` (with the grant command for the privilege) or `unchecked`; they never change the test's outcome. Proven by the new `g4-mongo` gate.

### Changed

- Lag, a lag alert and source setup checks for change capture (backlog `SRC-4`, slice 4; plan `docs/superpowers/plans/2026-10-29-src-4-databases-cdc.md`, migration `0118`). A change-capture connector has a **Change capture** tab on its page: Kafka Connect's state with Pause and Resume (moved from the Ingest tab), each table's lag ("Up to date", "Behind by 2m", "Not known yet", "Not known since <time>", "Paused") and the lag limit (1 to 1440 minutes, default 15). A new alert kind `connector_lag` is sent once when a table passes the limit and once when it is back under. `POST /api/connectors/{id}/test` of a PostgreSQL, MySQL or SQL Server change-capture connector lists `setupChecks`: `wal_level`, replication role, publication and its tables; the binary log, its format and row image, replication grants and a retention of at least 7 days; CDC on the database and each table and the Agent. A missing setting names the command that sets it; one the login cannot read is "Not checked"; the connector can be saved whatever they say. - MySQL and SQL Server change capture (backlog `SRC-4`, slice 3; plan `docs/superpowers/plans/2026-10-29-src-4-databases-cdc.md`). The applier reads SQL Server topics named `cdc.<id>.<database>.<schema>.<table>`. Two new CI gates, `g4-mysql` and `g4-mssql`, create a connector through the API with a least-privilege user and run first copy, a 120 s freshness budget, a pause with 20,000 changes per table, a `kafka-connect` restart during a stream of changes, a schema change and `DELETE`. **Limits:** a new SQL Server column needs a second capture instance (steps in the feature page); `verify-ca`/`verify-full` need the source's CA in Kafka Connect's trust store; the schema-history topic is not deleted with the connector; Debezium's `sys.sp_cdc_help_jobs` call needs `db_owner` and only logs a warning without it.
- PostgreSQL change capture runs per connector on Kafka Connect (backlog `SRC-4`, slice 2; ADR 0016; plan `docs/superpowers/plans/2026-10-29-src-4-databases-cdc.md`). ### Security

- Reading an uploaded workbook or a Parquet file can no longer end the API for every tenant (backlog `SEC-22`; plan `docs/superpowers/plans/2026-10-16-sec-22-upload-conversion-memory.md`, measurement `docs/plans/SEC-22-RESULT.md`). A file DECLARES how much memory its reader will want — the shared strings of an `.xlsx` are the worst case: the header of the part declares how many there are, and the reader reserves room for all of them before it reads one — and Rust ABORTS the process on an allocation failure, which `catch_unwind` cannot catch. The API therefore never parses an uploaded workbook or Parquet file in its own process: it starts this binary again as a child (`lakehouse-api inspect-upload`), which reads the file under a memory limit of its own (1280 MiB by default, `UPLOAD_CONVERT_MEMORY_MB`), so an allocation failure, a stack overflow or a CPU limit ends the child and never the API. The child is started with an empty environment, so no secret of the API reaches a process that parses an untrusted file. At most two conversions run at once per API process (`UPLOAD_MAX_CONVERSIONS`); over that the answer is 429 with `Retry-After: 5` and "Too many files are being read right now. Try again in a few seconds." A file that needs more memory or time than a read is allowed answers "This file needs more memory or time to read than an upload is allowed. Save it as CSV and upload that instead." **Behaviour change:** a workbook's sheet is converted once and stored, and the preview reads the stored text (the first 256 KiB of it) as it reads a text upload, so a second preview no longer parses the workbook, and the preview shows what fits in 256 KiB rather than the first 10,050 records. A Parquet file is read by RANGES and never whole: the child is given the file's tail (which holds the footer) and its first row group, so a file of the chunked route's 2 GB is previewed and loaded like a small one, and the API holds neither the file nor its footer.
- `DESCRIBE`, `DESC` and `SHOW COLUMNS FROM <table>` are tenant-gated like a `SELECT` (backlog `SEC-20`): the table they name must be the caller's to read, and a table that is not answers the same 404 sentence a refused `SELECT` gets, "Table not found or not available to your organisation"; nothing reaches the engine. A deployment with one tenant, a principal with every permission (`*:*`) and the catalog's own tenant behave as before.
- A statement that lists objects without naming a table (`SHOW TABLES`, `SHOW DATABASES`) is refused with a 422 and one fixed sentence for a member of a tenant that does not own the catalog (backlog `SEC-20`); a deployment with one tenant, a principal with every permission (`*:*`) and the catalog's own tenant are not affected.
- Sign-in counts each try before it checks the password (backlog `SEC-49`), so concurrent tries cannot exceed the lock: after the limit is reached, further tries are refused without a password check, exactly as a locked account is. A correct password still clears the count. No migration.
- `sqlx` moves from 0.8.6 to 0.9 across the workspace, which is what a connector's `VerifyCa` TLS dial needs (backlog `SEC-41`; spec `docs/core/specs/sec-41.md`, plan `docs/superpowers/plans/2026-10-24-sec-41-sqlx-0-9.md`; `SEC-14` part B rebases on it). `sqlx-core` 0.8.6's verifier recognised only rustls' `NotValidForName`, while rustls 0.23.46 reports `NotValidForNameContext`, so every dial that checked a CA while connecting to an approved IP address failed; 0.9.0 recognises both, and a test dials `127.0.0.1` with `PgSslMode::VerifyCa` against a certificate for `db.internal` (a TLS terminator in front of the test Postgres, chain minted per test) and refuses the same dial with a different CA. The `runtime-tokio-rustls` feature no longer exists: `runtime-tokio` plus `tls-rustls` is the same backend (ring, webpki roots), with `default-features = false` so 0.9's new `any` feature stays off. `sqlx` 0.9 refuses a statement built at run time unless it is wrapped in `AssertSqlSafe`, so the 100 call sites that pass a `format!`-built string now wrap it where it is passed, each with its reason beside it: only a constant column list or identifier is formatted into the text and every value is a bound parameter. `mysql-rsa` stays off, so a MySQL server with no TLS that asks for the password (`caching_sha2_password`, `sha256_password`) is refused with one fixed sentence instead of being sent an RSA-encrypted password, and `rsa` (`RUSTSEC-2023-0071`, no upstream fix) leaves the API binary — it stays a dev-dependency for OIDC and service-account test fixtures, so the advisory stays ignored, now with a justification that is true. Databases migrated by 0.8 start under 0.9 unchanged: a test replays 0.8's `_sqlx_migrations` table and rows, SHA-384 checksums included. `webpki-roots` 0.26 leaves `Cargo.lock` with `sqlx-core` 0.8.6, so `RUSTSEC-2026-0381`'s ignore is gone from `rust/deny.toml` and `.github/workflows/security.yml`. **Limit (closed by `SEC-14` part B):** a `VerifyCa` dial needs rustls' process-level default provider installed, and this workspace links two providers (`ring` through `sqlx`, `aws-lc-rs` through `tiberius`), so the first production dial would panic until one is installed at start-up. `SEC-14` part B installs `ring` there, so the dial no longer panics.
- `pymongo` 4.9.2 -> 4.18.2 in the Dagster code location (backlog `SEC-52`; plan `docs/superpowers/plans/2026-10-24-sec-52-pymongo.md`), fixing four open advisories: GHSA-v4x9-3549-crwv and GHSA-vp6j-j7w5-5xjj (high: a heap out-of-bounds write when encoding a BSON document, and host injection through percent-encoded delimiters in a connection string) and GHSA-qx36-8mw2-4r3x and GHSA-8fvv-fgr5-f8ch (moderate). The MongoDB adapter behaves as before: it hands hosts and credentials to `MongoClient` as keyword arguments, never as a URI string, keeps `directConnection=True`, classifies `OperationFailure` by `code` and connection failures by `pymongo.errors` class name, and converts `ObjectId`, `Decimal128` and `Binary` exactly as it did. **Limit:** 4.18 supports MongoDB 4.4 and later (4.14 dropped 4.0, 4.18 dropped 4.2), so a source still running 4.0 or 4.2 is no longer a supported server. `oracledb` and `paramiko` are unchanged, and `paramiko` 3.5.0's low advisory has no fixed release.
- The console sends a `Content-Security-Policy` on every page (backlog `SEC-47`; plan `docs/superpowers/plans/2026-10-23-sec-47-csp.md`). Scripts run only with the request's own nonce and `'strict-dynamic'`, so an injected inline script or one from another origin is refused; `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` and `frame-ancestors 'none'` close the other ways in. Images and web pages (the `BI-16` part B cards) may load only from the content sites in Admin > Settings, so a redirect from an allowed site is refused by the browser too: a console page reads the list from `GET /api/settings/reporting` with the visitor's session and reuses the answer for 60 seconds per process, an embed page reads its own dashboard's sites from `POST /api/embed/frame` (the same list that board's payload already carries, never the deployment list), and any failure — an unreachable or slow API, a `401`, a wrong-shaped answer — leaves no extra site and still loads the page. `style-src 'unsafe-inline'` is a stated exception: React, Radix and ECharts set inline styles, which a nonce cannot cover; it allows styles, never script. `next dev` adds `'unsafe-eval'` and the HMR websocket, a production build has neither. Every page now renders per request (`dynamic = "force-dynamic"` in the root layout), because a prerendered page would carry no nonce and the browser would refuse every script; no console page can be cached at a CDN. **Known limit:** a public link (`/public/dashboard/<token>`) is opened without a session, so it is served without the content sites and the browser refuses its image and web cards (an image card then says it could not be loaded; a web card stays blank); there is no `report-uri`, so a violation appears only in the browser console.
- JWT signing and verification use the `aws-lc-rs` crypto backend instead of RustCrypto, so `crypto-bigint` 0.5.5 leaves `Cargo.lock` (backlog `SEC-51`). `jsonwebtoken` 11.1.0's `rust_crypto` feature reached `RUSTSEC-2026-0387` (timing variability in modular reduction, with no patched 0.5 release) through `p256`/`p384` -> `ecdsa` -> `elliptic-curve` 0.13. The `aws_lc_rs` feature uses `aws-lc-rs`, already compiled into this workspace through `object_store`/`rustls`, so it adds no C dependency. The algorithms used here are unchanged: RS256, PS256 and ES256 signing (connector probe, GCP secret manager) and RS256/384/512 plus ES256/384 OIDC verification; the existing connector, secret-manager and OIDC tests exercise them. The lockfile loses 16 package entries and adds `untrusted` 0.7.1, a dependency of `aws-lc-rs`'s default features that the lock did not name before; no crate changes version.
- Queries and saved queries are scoped to the tenant (backlog `SEC-20`; feature page `docs/core/features/queries-scoped-to-the-tenant.md`). A statement that reads an uploaded table another tenant uploaded is refused with "Table not found or not available to your organisation: `<table>`", the same answer as for a table that does not exist, and never a 403 (Query Studio's Run all reads a 403 as "this user may not run anything" and would refuse the other statements too). The check sits in the shared query rewrite, so Query Studio's run, estimate and download, the chat's `run_sql`, `propose_sql` and `run_saved_query`, and a catalog table's sample and profile all get it. The caller's tenant is the `X-Tenant` header when one is sent, else the caller's first tenant; a principal holding every permission (`*:*`) passes; a deployment with one tenant behaves as before. A saved query belongs to the tenant that saved it: the list in Query Studio, the list in the chat and a table's "used by" list show the caller's tenant's rows, plus the rows saved before this change for the tenant that owns the catalog, and a saved query of another tenant can neither be listed nor run. **Limits:** dashboards, scheduled exports, alerts and authored pipelines are not scoped this way yet (they call the role rewrite directly, not the query path); Silver and Gold tables belong to the shared catalog, so with more than one tenant only the tenant that owns the catalog can query them. Migration `0099_saved_query_tenant.sql`.
- A row filter prints as it was checked (backlog `SEC-44`, a follow-up of `SEC-32`). A unary `-` or `+` over another sign, a control character in a text value, and `LIKE ANY` in a row filter are refused: `sqlparser` writes a unary sign with no space before its operand, so a checked `x = - -1` printed as `x = --1` and read as a `--` comment, and a text value could print across lines. A policy that breaks this refuses queries on its table until the policy is edited.
- `ctutils` 0.4.2 -> 0.4.4 in `Cargo.lock` fixes `RUSTSEC-2026-0385` (non-constant-time mask generation and `u128` comparisons in `ctutils::Choice`, published 2026-10-23), which turned `cargo audit` and `cargo deny` red (backlog `SEC-48`).
- Bundled root certificates no longer trust the distrusted emSign intermediates (backlog `SEC-46`). `RUSTSEC-2026-0381`, `RUSTSEC-2026-0382` and `RUSTSEC-2026-0383` are fixed in `Cargo.lock` by `rustls-webpki` 0.103.15 -> 0.103.16, `webpki-root-certs` 1.0.9 -> 1.0.10 and `webpki-roots` 1.0.9 -> 1.0.10. `webpki-roots` 0.26.11 (required by `sqlx-core` 0.8.6) has no patched release but is a shim that re-exports `webpki-roots` 1.0.10, so `RUSTSEC-2026-0381` is ignored for it in `rust/deny.toml` and `.github/workflows/security.yml`. The exception will be dropped when `sqlx` moves to 0.9 (`SEC-41`) and `webpki-roots` 0.26 leaves the lockfile.
- Transitive zip advisories ignored with checked rationale (backlog `SEC-42`; plan `docs/superpowers/plans/2026-10-17-sec-42-zip-advisories.md`). `RUSTSEC-2026-0367`, `RUSTSEC-2026-0368` and `RUSTSEC-2026-0369` in `zip` 8.6.0 are ignored in `rust/deny.toml` and `.github/workflows/security.yml`. All three advisories affect `zip::extract` writing archives to disk, which is not reachable from this workspace: `zip` is pulled in only transitively through `calamine` 0.36.1 (`calamine` <- `lakehouse-api`), which reads archive entries in memory using `by_name` and never calls `extract`. The workspace has no direct `zip` dependency. The exceptions will be dropped when `calamine` accepts `zip` >= 9.0.0.
- Upload limits and CSV files that cannot run a formula (backlog `SEC-17`; feature page `docs/core/features/upload-limits-and-safe-csv.md`). A file with more than 1,000 columns is refused: `GET /api/uploads/{id}/preview` and `POST /api/uploads/{id}/ingest` answer 400 "The file has more than 1,000 columns." (ingest before any table claim, mark or launch), the Check step shows the sentence and keeps its delimiter, encoding and header row controls, and the load job records the same sentence as a new eighth failure reason (`ops/fixtures/upload_load_failure_reasons.json`). Files being received (`POST /api/uploads`, counted in the API process, taken before the body is read) and loads running (rows in `ingesting`, counted in Postgres under an advisory lock) are limited to `UPLOAD_MAX_CONCURRENT_PER_USER` (default 4) and `UPLOAD_MAX_CONCURRENT` (default 16), each against both; over either the answer is 429 with `Retry-After: 5` and "Too many uploads are in progress. Try again in a moment."; a value that is not a whole number of 1 or more stops the API at start. A load is counted against the person the upload records (`uploaded_by`), not whoever pressed Load. A CSV file the console writes (a table's "Export CSV", a dashboard tile's download, Query Studio's "Download CSV", the API's `GET /api/query/run/{id}/download?format=csv`) now puts `'` before a cell whose first character is `=`, `+`, `-`, `@`, a tab or a carriage return, unless the whole cell is a plain number (`-5` and `+3.2e4` stay numbers); Parquet downloads are unchanged. Limits: the count of files being received is per API process; a program that reads an export back gets `'=A1`, not `=A1`. No migration. The Rust tests of this change were written but not run on the machine they were written on; the pull request's CI runs them.
- A pipeline reads as its author (`BLD-1`, slice 1; plan `docs/superpowers/plans/2026-10-15-bld-1-run-as-author.md`). Authored pipelines now execute their source queries through the same masking and row-filter rewrite that Query Studio, alerts, and dashboards apply, reading as the pipeline's author rather than unmasked through the orchestrator. Creating a pipeline records the user who created it (`pipeline_definition.run_as`), and the pipeline details page shows "Reads as: <name>". A Platform Admin can reassign who a pipeline reads as (`PUT /api/pipelines/{id}/run-as`). **Behaviour change:** Existing pipelines without a recorded author (and pipelines whose author was removed or deactivated) fail closed and stop running until an administrator assigns one, failing with the fixed reason "this pipeline has no author to read as; an administrator must assign one". The console displays this reason and provides an assignment control for administrators. Migration `0076_pipeline_run_as.sql` adds `run_as` to `pipeline_definition` (referencing `app_user.id`) and backfills it from each pipeline's initial version `changed_by` where present.
- The assistant can no longer confirm its own change (backlog `AI-18`). The chat loop drops a `confirmed` flag from the model's tool arguments before the approval gate, so a low-risk write such as `create_chart` or `create_board` waits for the Confirm button. Only the Confirm button can send that flag.
- The assistant's data map now needs `catalog:read` (backlog `SEC-24`). The chat's system prompt gives the tables, row counts and column facts only to a user with `catalog:read`. Column ranges, which come from `/api/catalog/{id}/profile`, and sample values, which come from `/api/catalog/{id}/sample`, go only to a user who also has `query:read`, the permission both routes require. Of the seeded roles, Platform Admin, which holds `*:*`, and Analyst get the full map. Governance Admin gets `catalog:read` from migration `0031_governance_admin_catalog_read.sql` but no `query:read`, so it gets the map without ranges and sample values. Approver, Data Engineer, Data Scientist and Dashboard Viewer get no map, since none of them holds `catalog:read`.
- Query Studio's cost estimate refuses a statement that is not a read, as a run already does (backlog `SEC-19`).
- A ClickHouse run stops at the result cap inside the engine, so a huge result no longer fills the API's memory. A statement may use SETTINGS only for `iceberg_snapshot_id`, the version picker's setting, so no statement can lift that cap (backlog `SEC-21`).
- A row filter's text value cannot contain a backslash (backlog `SEC-32`). The policy check and ClickHouse read a backslash differently, so the filter that was checked could differ from the filter that ran. A row filter now accepts only plain `'text'` values, numbers, booleans and NULL. A policy that breaks this refuses queries on its table until the policy is edited.
- The row-filter check looks at every part of a function call, every operator and every table name before a column. A call may not carry `FILTER`, `OVER`, `WITHIN GROUP`, a second parameter list, `DISTINCT`, a null treatment, a clause inside the parentheses or the ODBC `{fn ...}` form. An operator outside the comparisons, `AND`, `OR` and `+ - * / %` is refused. A column may have one plain table name before it (backlog `SEC-43`, a follow-up of `SEC-32`).

### Added

- Query Studio results you can use (backlog `QS-2`; feature page `docs/core/features/query-studio-results.md`). A run shows up to 64,000 rows or 10 MB of row data, whichever comes first, and a banner says which limit cut it. The result grid can be filtered per column, profiled per column (empty cells, distinct values, min and max, a histogram over the rows shown), inspected cell by cell (a long value or JSON, pretty-printed), and copied as TSV. The whole result can be downloaded from the server as CSV, TSV, Excel or Parquet, up to 5 GB, with the masks and row filters the run had; a download in progress can be stopped with Stop, and the time a run has taken is counted while it runs. Migration `0116_query_studio_rows_default.sql`. **Limits:** the grid's filters and statistics cover the rows shown, not the whole result; a download re-runs the query, so the file shows the data as it is at the moment of the download; a comma or tab file over 5 GB is cut at the last whole row that fits and says so in its name, while a Parquet result over 5 GB is refused whole; Excel stops at 1,048,575 data rows (1,048,576 with the header); downloads run on ClickHouse only.
- Folders for uploaded files (backlog `DATA-35`; plan `docs/superpowers/plans/2026-10-26-data-35-upload-folders.md`, feature page `docs/core/features/upload-folders.md`). The Uploaded files tab on Sources now has a folder column: All files, No folder, and the tenant's folders, nested up to 3 levels. Make a folder (also inside another), rename it, move it, and delete it once it holds no file and no folder; the Delete control is off, with the reason, while it holds either. Tick files and move them to a folder, or out of any, in one step. The tab has a search box that covers every folder and shows each match's folder. On the Table step of an upload, pick a folder (or make one there); a table an earlier upload loaded offers that upload's folder. The step sends the folder it shows, so "No folder" puts the file in none and the table remembers no folder; a load that names no folder at all joins the table's remembered one. A folder only groups files on the tab: a file's table keeps its name, and nothing a pipeline, chart, saved query or lineage reads changes. Folder names are unique among the folders in the same place, ignoring case; folders belong to the tenant and are managed with `connector:manage`, as uploading is. New routes: `GET` and `POST /api/uploads/folders`, `PATCH` and `DELETE /api/uploads/folders/{id}`, `POST /api/uploads/move`; `GET /api/uploads` takes `folderId=<id>|none` and `q=<text>` and each upload carries `folderId`; `POST /api/uploads/{id}/ingest` takes `folderId`. - Reusable metrics and segments (backlog `BI-2`, with the assistant's `AI-7`; plan `docs/superpowers/plans/2026-10-11-bi-2-reusable-metrics.md`, feature page `docs/core/features/reusable-metrics.md`). A metric is a name, a description, an aggregate formula (the language of calculated fields), the table or SQL source it is computed from, filters of its own, and an optional date column and default period; a chart or a KPI picks it by name (`{ "metric": ... }` as a measure, marked *metric* in the picker with its description on hover), stores the name and not a copy, and so every chart shows the same number and a changed metric reaches all of them at the next read. The metric's filters apply to its own number only: each aggregate in the formula takes them as its condition, so a filtered metric and an unfiltered measure can share one chart and one grouping. A segment is a saved list of filters on one table ("domestic visitors"), used inside a metric and as a chart filter (`{ "segment": ... }`). A chart that names a metric or segment that is missing or no longer checks out shows that on its tile; it never runs the statement saved with the chart. The assistant lists metrics before writing SQL (`list_metrics`, `describe_metric`, `query_metric` read the number as the signed-in person; `create_metric` and `update_metric` need `metric:write`; `delete_metric` waits for approval) and names the metric it used. If the metric is gone or cannot be evaluated the rule is recorded as skipped with a fixed reason; it never fires and is never treated as fine. A metric watched by a rule cannot be deleted; the refusal names the rule. A statement that mixes a metric with a measure of the same name as a column of the table now asks the engine to prefer the column (`prefer_column_name_to_alias`), which it needs to run. **Not included:** certified metrics (they wait for `DATA-12`, which does not exist yet), metrics across several tables, and goals and approval flows.

- Parquet files (`.parquet`) in the file upload (`DATA-9`; plan `docs/superpowers/plans/2026-10-07-upload-excel.md`, section 11; ADR 0014, amendment of 2026-10-08). On Sources, Upload file accepts a Parquet file of up to 50 MB. A file has one table and its own column names, so the Check step has no sheet, encoding, delimiter or header-row control: it shows the first rows with each column's declared type under its name ("was: int64") and the row count the file states. The API stores the file as it arrived, converts it to UTF-8 comma-separated text in memory for the preview (only the rows shown are decoded), and for the load stores the whole text beside the original (`<key>.converted.csv`, removed with the upload) and launches the unchanged `file_ingest_job` on it; the first record is the file's column names. Every column is text, written like this: null as empty; an integer as its digits; a `float` or `double` in the shortest form that reads back the same (`0.1`, `1e-7` and `1e21` in exponent form, as for a workbook); a decimal with its exact digits and scale (`12.50`), never through a float; a boolean as `true` or `false`; a date as `2025-09-24`; a timestamp as `2025-09-24T13:30:05.123456` (the fraction only when there is one, exact to the unit the file uses), with a trailing `Z` when the column is adjusted to UTC and none when it is a local time; a legacy `INT96` timestamp as a local time, read as microseconds so a year outside 1677 to 2262 does not wrap; a time of day as `13:30:00`. A value no calendar date can hold is written as the integer the file holds. Refused with the reason: a file with a binary or nested column (list, map, struct), naming the first such column and its type; an encrypted file; a file that does not open; a file of more than 5,000,000 cells (rows times columns, decided from the file's footer before any row is decoded) or whose text would pass 512 MB. A text file named `.parquet` is still read as text, and a Parquet file not named `.parquet` is refused with the reason. New in the API: `parquet` (`columns` with `name` and `type`, and `rows`) in the answers of `POST /api/uploads` and the preview; the load body's `encoding`, `delimiter`, `headerRow` and `sheet` are not read for a Parquet file; the `upload.ingest` audit event says `"format": "parquet"`. The refusal sentences for a workbook and for another binary now list `.parquet` among what is accepted, and a Parquet-shaped file under another name has its own. No migration; the `parquet` crate was already in the lockfile (through the Iceberg client) and is now also declared by the API crate with the same features, so no crate and no licence is added. Not included: typed columns, binary and nested columns, `uuid` stored as bytes.

- Schema changes at the source (`SRC-8`; plan `docs/superpowers/plans/2026-10-09-src-8-source-schema-changes.md`; measurements `docs/plans/SRC-8-RESULT.md`). Before a table of a PostgreSQL, MySQL, MariaDB, SQL Server or Oracle connector loads, its columns and primary key are compared with the last accepted ones: added and removed columns, changed types and a changed key are recorded and shown on a new "Schema changes" tab of the connector's page, and raise the "schema changed" alert. ### Security

- **TLS required for connector dials and plaintext passwords refused before transmission (`SEC-14` part B, decisions E1–E4).**
  - PostgreSQL connector test (`POST /api/connectors/{id}/test`): replaced the sqlx connection test with a wire-level probe client (`pg_probe`) that requires TLS via `SSLRequest` before the startup message is sent, only negotiates `SCRAM-SHA-256` authentication, and immediately terminates the connection without sending a password if the server requests clear-text (`AuthenticationCleartextPassword`) or MD5 (`AuthenticationMD5Password`) authentication. When `CONNECTOR_TLS_CA_FILE` is configured, verifies the server certificate and hostname (`verify-full`); otherwise encrypts the connection (`Require`).
  - PostgreSQL sqlx dials: table discovery (`connector_discover`), table listing (`connector_listing`) and change-capture publication clean-up (`connector_deprovision::drop_slot_and_publication`) require TLS (`PgSslMode::Require` when no CA is set, `PgSslMode::VerifyCa` with the root certificate when `CONNECTOR_TLS_CA_FILE` is configured), eliminating `PgSslMode::Prefer`. `VerifyCa` proves the chain and skips the name check, because these dials go to the approved address rather than the name (`SEC-15`); the connection test's own client is what checks the name.
  - SQL Server dials: connector probe, discovery, and table listing (`connector_listing`) enforce encryption (`EncryptionLevel::Required`), verifying the server certificate against the CA via Tiberius's `trust_cert_ca` when `CONNECTOR_TLS_CA_FILE` is configured.
  - Docker Compose: bundled PostgreSQL runs with `ssl=on`, configured with a self-signed CA and server certificate (`DNS:postgres`) generated into a named volume by `postgres-cert-init`. `lakehouse-api` mounts this CA at `/run/certs/postgres/ca.crt` with `CONNECTOR_TLS_CA_FILE` set by default, enabling `verify-full` for the seeded connector `conn-pg-lakehouse`.
  - The API binary installs `ring` as rustls' process-level default provider before it starts any task (`lakehouse_api::crypto_provider::install_default_provider`). The workspace links two providers (`ring` through `sqlx`, `aws-lc-rs` through `object_store`/`hyper-rustls`), and rustls cannot choose one on its own, so the first TLS dial would otherwise panic with "Could not automatically determine the process-level CryptoProvider".

- **History secret scan scoped to `HEAD` on `main` and pull requests (`SEC-36`, decisions D1–D2).** In `.github/workflows/security.yml`, the `history-scan` job no longer fetches all branches and runs `gitleaks detect` with `--log-opts="HEAD"`, scanning only `main`'s history or `main` plus the pull request's commits. Unrelated branches carrying findings (such as `#144`) no longer turn `main` or other pull requests red. A separate daily workflow (`.github/workflows/security-all-branches.yml`, cron `17 3 * * *` and `workflow_dispatch`) scans all branches across the repository history with `--log-opts="--all"`, failing loudly when any branch carries an un-baselined finding without blocking unrelated pull requests.
- **The Query Studio download applies the same policy rewrite as the run.** The download re-ran the stored statement without the role-based masks and row filters the run applies; it now rewrites the statement for the caller's current roles with the same function the run uses, and a statement the rewrite refuses is refused with the run's status and fixed message and is never sent to the engine.
- **The cost estimate and the assistant's dry run explain the rewritten statement.** `POST /api/query/estimate` and the `run_sql` tool's engine dry run now apply the same policy rewrite as the run, for the caller's current roles, before the engine is asked anything; a statement the rewrite refuses is refused with the run's status and fixed message and is not sent. The tables an estimate lists are unchanged by the rewrite. A statement the rewrite cannot read now gets the run's refusal from the estimate instead of a 200 carrying an `error`.

Five changes. (1) Compose now blocks internal addresses unless `CONNECTOR_PROBE_ALLOW_INTERNAL_HOSTS=true` is set: it used to default to `true`, and `.env.example` set it, so a fresh install allowed them. An install that copied the old `.env.example` keeps its `true` until the operator changes it. On a fresh install the seeded demo connectors, which point at `postgres:5432` and `http://rustfs:9000`, are refused until the operator opts in; `CONNECTOR_PROBE_ALLOWED_CIDRS` is the narrower choice. (2) The REST test no longer follows redirects (it followed up to ten after checking only the first host); a redirect is reported with a fixed message. The S3 test follows none either. (3) The address the check approves is the address that is dialled, for PostgreSQL, MySQL and MariaDB, SQL Server, REST and S3, in the test and in discovery; the name is no longer resolved a second time. `reqwest` 0.13 is now a direct dependency of `lakehouse-api` (the version `object_store` already used) to pin the S3 client. A system proxy is no longer used for these two tests. (4) Deleting a change-capture (PostgreSQL) connector runs the same check before it dials the source database to drop the replication slot; a refused target is a 409 with a fixed message and the row stays, and `?force=true` removes the row without dialling it. (5) Refusals are fixed sentences: they repeat the host the caller typed and never the address it resolved to or the resolver's text. The delete's 409 and the log no longer carry `sqlx` text either. The block list also gained multicast, carrier-grade NAT (`100.64.0.0/10`), the rest of `0.0.0.0/8`, the reserved block `240.0.0.0/4`, IPv6 site-local, and IPv4 inside IPv4-compatible and NAT64 addresses; `CONNECTOR_PROBE_ALLOWED_CIDRS` can open carrier-grade NAT but still never opens `0.0.0.0/8`, multicast, loopback or link-local. Still open: "connection refused" and "timed out" differ in a test result, so a caller who may test connectors can still tell an open port from a closed one on an address that is allowed; TLS and certificate checks are `SEC-14`.
- The range of a masked numeric or date column no longer reaches the copilot's prompt or the model that drafts descriptions; the column is still listed with its name and type.
- No response carries the text of an upstream error any more (backlog `SEC-11`; plan `docs/superpowers/plans/2026-10-10-sec-11-no-raw-upstream-errors.md`; feature page `docs/core/features/no-raw-upstream-errors.md`). A failed dashboard tile, on the console, a public link and an embed, used to print `ClickHouse`'s own message (table names, the server version); so did the 500 bodies of the public and embed routes, the assistant's tools, the SQL editor and its cost estimate, and many catalog, alert, pipeline, connector, storage and overview routes. The full error is written to the API log at `error` (at `warn` when the service could not be reached), with the same id, after URL credentials and `password=`-style values are masked and the text is cut at 2,000 characters. Messages the product writes itself (a malformed body, a refused statement, "not found", permission and policy refusals) are unchanged, and so are the status codes, with these exceptions: an unreachable `ClickHouse` is now `503` where a few routes said `422` or `500`; a `ClickHouse` failure while saving a chart or a board is reported at its old status (`400`/`500`) but a `lakehouse_bi` error in `dashboard.rs` now follows the dashboard store's `503`. The "fourteen Phase-1 handlers" gap in `AGENTS.md` is closed. No migration, no new route, no new dependency.
- Alert and digest webhooks can no longer be used to reach the server's own network (backlog `SEC-10`; plan `docs/superpowers/plans/2026-10-10-sec-10-webhook-internal-addresses.md`; feature page `docs/core/features/webhooks-cannot-reach-internal-addresses.md`). The webhook sender used to check only that a URL began with `http://` or `https://`, so anyone who may create alerts could make the server call a service inside the customer's network, the cloud metadata address or the server itself, and a public URL could bounce the call inward with a redirect. Now a webhook to loopback, a private (RFC1918) address, link-local, carrier-grade NAT, multicast or a reserved range, or to a name that resolves to one (also when wrapped in an IPv6 address), is refused with "webhook address is not allowed": a rule that points at one cannot be saved (`POST`/`PUT /api/alerts`, and the assistant's alert tools, answer 400), and the check runs again at every send because a name can resolve differently later. It is the same set of addresses the connector tests refuse. The host is resolved once and the request goes to the address that passed, so the name cannot change in between; an `https` webhook still verifies the certificate against its host name. A redirect is not followed: a webhook that answers 3xx is a failed delivery, "webhook redirect not followed". A delivery now gives up after 10 seconds (there was no limit) and ignores a system proxy (a proxy resolves the name itself). A failed delivery records one of a few fixed reasons ("webhook host could not be resolved", "webhook HTTP <status>", "webhook request timed out", "webhook connection failed", "webhook request failed"), never the HTTP library's text, which could contain the URL; deliveries recorded before this change keep what they have. An administrator can allow an internal target with the new `WEBHOOK_ALLOWED_CIDRS` (empty by default; same format as `CONNECTOR_PROBE_ALLOWED_CIDRS`, which it does not share; no allow-everything form; loopback, link-local, multicast and `0/8` can never be listed; a malformed entry stops the API at start). Webhooks that point at an internal chat or incident tool stop working until it is listed. No migration, no new route, no new dependency. Not included: email (`SMTP`), per-rule allowlists, retries.
- A statement the assistant's SQL tool is not allowed to run (a table function, or a system table that lists other users' queries) is now refused before any part of it is sent to the database, where before the database's query log still received it as a syntax check (backlog `SEC-9`; plan `docs/superpowers/plans/2026-10-10-sec-9-natural-language-queries.md`; feature page `docs/core/features/natural-language-queries-respect-permissions.md`). Nothing was fetched either way; the refusal and its message are unchanged.
- Signed embed tokens always expire, can be withdrawn, are signed with a secret you configure, and the embed pages can only be framed by sites the dashboard's owner listed (backlog `SEC-12`; plan `docs/superpowers/plans/2026-10-10-sec-12-safer-embed-tokens.md`; feature page `docs/core/features/safer-embed-tokens.md`). A token must carry `exp` and `iat` (Unix seconds, both numbers), its lifetime `exp - iat` may be at most `EMBED_TOKEN_MAX_LIFETIME_SECONDS` (default 86400, 24 hours; a value that is not a positive whole number stops the API at start), `iat` may not be in the future and `exp` may not be in the past, each with 60 seconds of tolerance for a clock difference. An optional `jti` (1 to 128 characters of `A-Za-z0-9._-`) lets one token be withdrawn on its own. Every refusal of a signed token, whatever the reason, answers `401` with the one message "embed token is invalid or expired"; with no secret configured, `POST /api/embed/data` answers `503` "embedding is not configured". In the Share dialog the owner can withdraw all of a dashboard's tokens (those issued at or before that moment are refused from the next request, and in any case within a minute), withdraw one token by pasting it (`POST /api/dashboard/embed-revoke`; the server reads the `jti` from the signed token, a bare id is not accepted, and a token without a `jti` is told it can only be withdrawn with the others), and list the sites allowed to frame the embed (at most 20; `https://host[:port]`, or `http://localhost[:port]`; no wildcard). The embed pages (`/embed/signed/...` and `/embed/dashboard/...`) answer with `Content-Security-Policy: frame-ancestors <those sites>`, or `frame-ancestors 'none'` when none are listed, the token is not known, or the API cannot be asked. `GET /api/dashboard/embed-info` now also returns `supported`, `reason`, `maxLifetimeSeconds`, `revokedBefore` and `allowedOrigins`. Public links (`/public/dashboard/...`) have no new check, except that their iframe page (`/embed/dashboard/...`) now needs the listed sites too. Three **breaking** changes on upgrade: (1) embed tokens without `iat` and `exp`, or living longer than the limit, stop working at once, with no grace setting; sign a fresh token per page view or session, with `iat`, `exp` and optionally `jti` (see `docs/OPERATIONS.md`). (2) An embed shows nothing until the dashboard's owner lists the embedding site in the Share dialog; this includes the public link's iframe. (3) The API no longer invents an embedding secret and stores it in `console.app_kv`: a deployment that relied on it must set `EMBED_SECRET` (and sign with that value), and until it does signed embedding is unavailable; the API still starts. An existing `embed_secret` row in `console.app_kv` is no longer read and should be removed by the operator. No migration: the board's three new columns are added at start by the same `ADD COLUMN IF NOT EXISTS` bootstrap the others use. No new dependency. Not included: expiry or password for public links (`BI-19`), secret rotation with an overlap, framing headers for the rest of the console. Known limit: "withdraw all" compares the API's clock with the token's `iat`, so a token minted by a clock running up to 60 seconds ahead of ours survives it until it expires.

- Governance `GET /api/governance/{kind}` now unions authored rules into
  the response.
- Infra endpoint URLs and credentials made env-only — no internal defaults
  baked into source.
- Remaining admin routes gated on the new permissions model; ad-hoc
  `/api/*` fetch calls in the frontend routed through the central
  `apiFetch` (and its 401 handling) instead of calling `fetch` directly.

### Fixed

- Every JSON response now emits `application/json;charset=utf-8`
  consistently.
- ClickHouse and Dagster clients no longer leak internal endpoint URLs on
  transport failure.
- Invalid `SMTP_PORT` degrades gracefully (falls back to `587`) instead of
  failing boot; `SMTP_SECURE`'s effective value now folds in the
  `port === 465` rule from the original TypeScript, not just the raw env
  var.
- Request-timeout responses render as a proper JSON error envelope instead
  of a bare timeout.
- Stale `#[allow(dead_code)]` on `ApiRejection`/`ErrorBody` removed once no
  longer needed.
- BI: stopped dropping every live stored chart on the new envelope shape.
- Stale `pub mod tenant;` dropped from `lib.rs` (the tenant module is not
  wired into any route — see the Security section of the release notes for
  what this does and does not mean for tenant isolation).
- `docker compose`: `lakehouse-api`'s runtime base image matched to the
  builder's OS; built from a pinned Rust 1.96.1 `Dockerfile`.
- Nested `if let` chains collapsed for clippy on current stable.
- `must_change_password` now enforced server-side, not just as a UI hint.
- `gitleaks`'s full-history job fixed to actually detect the key it was
  missing, then to stop flagging its own scanner config and docs as new
  matches.

### Security

- **Unauthenticated API surface** — before the `lakehouse-auth` core was
  wired into the router, every route (including writes to Postgres-backed
  storage) was open. Fixed by introducing `Principal`/`Authenticator` and
  gating the router on `crate::policy`'s deny-by-default `POLICY_TABLE`.
- **`/api/identity/*` privilege escalation** — identity routes were
  auth-gated but not permission-gated, allowing any authenticated caller to
  reach admin-only identity operations. Fixed by permission-gating those
  routes (D1).
- **Embed signing secret returned over HTTP** — a dashboard-embed response
  was returning the HMAC signing secret used to sign embed tokens. Fixed by
  no longer including it in the response (D2).
- **`ai/chat` executing write tools in read-only mode** — the write-tool
  block was previously enforced only at advertisement time (tools were
  hidden from the model) but not at dispatch time, so a crafted tool call
  could still execute a write. Fixed by enforcing the block at dispatch
  (D3).
- `/api/alerts/run` now fails closed (401) when `ALERTS_RUN_TOKEN` is unset,
  instead of allowing unauthenticated calls (D4).
- `Config`'s `Debug` implementation hand-written (not derived) so secret
  fields (`ch_password`, `llm_key`, `embed_secret`, `alerts_run_token`,
  `smtp_pass`, `database_url`) can never leak into a `{:?}`-formatted log
  line; enforced further by a `check-no-secrets.sh` CI script after a
  secret was leaked once during development.

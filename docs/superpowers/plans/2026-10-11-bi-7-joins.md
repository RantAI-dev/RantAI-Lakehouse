## 1. Decisions already made (do not re-ask, do not change)

| Decision | Choice |
| --- | --- |
| Definition | Optional `joins` on `ChartInput`: 0 to 4 entries, each `{ "mart": <a table of the serving layer>, "type": "inner" | "left" | "right" | "full", "on": [ { "left": <column of the base or of an earlier join>, "op": "=" | "<" | "<=" | ">" | ">=", "right": <column of this table> } … ] }` with 1 to 4 pairs, at least one of them `=`. Absent on every chart saved before. Only for charts on a mart, not on a SQL source. |
| Flat relation | A join is a new `Relation` that projects the base table's columns under their own names and each joined table's columns under `<alias>__<column>`, where the alias is the table's name (a number appended when the same table is joined twice) and the whole name is a valid `Ident`. Everything downstream (dimension, breakdown, measures, chart filters, dashboard filters, grain, tables, pivots, steps) reads that flat relation unchanged. A base column and a joined column never collide. The console shows `<alias>__<column>` as `table.column`. |
| Columns and types | The save path and the `fields` route return the joined relation's columns with their kinds, so pickers, grain and filters work. A column name that would exceed the identifier rules is refused at save with a plain sentence. |
| Calculated fields | Fields of the base table keep working. A field cannot reference a joined column in this slice: refused with a positioned message. |
| Dashboard filters | A dashboard filter on a column name applies to the base table's column of that name, as today. It does not reach joined columns unless the dashboard filter names the `<alias>__<column>` form (which the tile's `filterFields` now lists). |
| Permissions | Each table in the join is read through its own masked and row-filtered projection for the caller's roles. A table the caller's role cannot read at all refuses the chart. The statement is built so the role rewrite sees every table reference as a plain table reference; if a shape hides one from the rewrite, that is a stop-and-report, not a workaround. |
| Engine limits | The statement runs under the settings tiles already use, plus the engine's own join memory limit left in force. An engine refusal for size reaches the tile as the fixed message with a reference (`upstream_error`); it is never turned into a partial result. `join_use_nulls = 1` so an outer join's missing side is null, not a default. |
| Suggestions | `GET /api/dashboard/join-suggestions?left=<mart>&right=<mart>` (`dashboard:read`): candidate pairs ranked by: both in the tables' sorting keys, same name and compatible kind, same name. Returns also whether the suggested right-hand columns cover the right table's sorting key (the console's "rows may multiply" warning when they do not). Reads only column metadata the caller may already see through `fields`. |
| Records and export | The record list of a clicked value and the CSV export of a raw table read the joined relation, so joined columns appear. |
| Assistant | `joins` in the `create_chart` / `update_chart` schemas; a `suggest_join` tool (read) wrapping the suggestions route, named in `src/features/copilot/capabilities.ts`; `tool_schemas.json` regenerated and the tool count assertion updated. |
| Export | `chart_def_fields` lists `joins`. |

## 2. Tasks

- **T1 — `lakehouse-bi`:** `joins` on the definition and its validation; the joined `Relation` and its projection; column kinds for the joined relation; refusals. Unit tests per join type, per operator, two joins, the same table twice.
- **T2 — API:** `fields` for a join; the suggestions route with policy and auth tests; preview, dashboard, records, export, embed and public paths; assistant schema, tool and fixture.
- **T3 — Console builder:** a "Joins" section under Data source (add a table, type, pairs with suggestions applied by default, the multiply warning), joined columns in every picker as `table.column`; `previewKey` and `previewSpec`.
- **T4 — Console tiles:** labels for joined columns in headers, legends and filter chips.
- **T5 — Docs:** `CHANGELOG.md` `[Unreleased]`.

## 3. Out of scope (do not build)

Joining SQL sources; unions; calculated fields over joined columns; saved joined datasets; cross-database joins.

## 5. Things the developer must verify, not assume (not reduced)

Against the dev `ClickHouse` (26.8) and the real role rewrite, statements and results quoted:

- `BI-7-AC1`: visitors and rooms by province through the builder's statement equal a hand-written join, for inner, left, right and full; the full join shows the two visit-less provinces with empty visitors.
- `BI-7-AC2`: with the real `enforce`, a mask on a column of the joined table and a row filter on the joined table, and separately on the base table: the rewritten statement reads each table only through its governed projection, and the results show the mask and miss the filtered rows. The same with the same table joined twice.
- A role with no access to the joined table is refused, and nothing about that table's columns leaks through `fields` or the suggestions route.
- Row multiplication: a join on a non-key column changes `sum(visitors)`; the warning flag is set for it and not set for the key join.
- Dashboard filters, chart filters (`BI-6`), a grain and a pivot over a joined relation each run.
- Charts saved before this change produce byte-identical SQL.

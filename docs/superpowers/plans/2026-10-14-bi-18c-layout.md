## 1. Decisions already made (do not re-ask, do not change)

| Decision | Choice |
| --- | --- |
| Tabs | Optional `tabs` on a board: an ordered list of `{ id, title }` (1 to 20, titles 1 to 60 characters); every tile in `layout` carries the tab it sits on. A board without `tabs` is one implicit tab and renders exactly as today. Adding the first tab puts every existing tile in it. Deleting a tab requires it to be empty, or moves its tiles to the first tab (the editor chooses). The selected tab is in the page URL. |
| Filters and tabs | A dashboard filter has optional `tabs` (a list of tab ids); absent means every tab. A tile on a tab the filter is not tied to ignores it and is not marked as skipped. Saved with the filters, as today. Grain and parameter controls (`BI-9`, `BI-11`) apply to every tab. |
| Sections | Three tile kinds without data: `heading` (text, one line), `divider`, and a `section` header (a heading that folds the tiles below it up to the next section header on the same tab). The existing `text` kind stays. Folding is a viewer's own state (kept in the browser), not saved. They take no SQL and never run a statement. |
| Phone and tablet | Below 640 px the grid renders one column with every tile full width, ordered by the layout's reading order (row, then column), sections and tabs kept. An editor may save a separate `phoneLayout` (order and heights only; widths are always full) in an "Edit phone layout" mode; when present it replaces the computed order below 640 px. Embeds and public links follow the same rule. |
| Duplicate | Duplicating copies tiles (as new chart ids with the same definitions), tabs, filters (with their tab ties), grain, parameter controls, refresh, layout and phone layout; the copy's name is "Copy of <name>". The built-in board can be duplicated (its fixed SQL tiles become ordinary saved charts if the store allows, otherwise they are omitted with a sentence in the copy's description saying so — say which in the handoff). Embedding settings and tokens are never copied. |
| Version history (part 2) | `console.bi_board_version`: board id, version number, the board's full state as JSON (board fields plus its charts' definitions), author principal, time. Written on every successful board or chart write that changes the board's content; the last 15 kept per board. Revert writes the stored state back as a new version. Routes `GET /api/dashboard/versions?board=` (`dashboard:read`), `POST /api/dashboard/versions/revert` (`dashboard:write`). |
| Trash (part 2) | Deleting a board or chart sets a `deleted_at` instead of removing it; deleted items are excluded from every read path (dashboard, embed, public, search, usage, assistant tools) and listed under "Trash" for 30 days with restore. A background sweep (on the existing scheduler) removes items older than 30 days. Restore needs `dashboard:write`. A chart restored onto a deleted board goes back with the board, or to "no dashboard" if the board is gone. |
| Personal space (part 2) | A per-user folder created on first use, visible to its owner and to principals with `identity:write` only, enforced on every read path including search, embeds (cannot be shared from it) and the assistant's tools. |
| Favourites, recent, search (part 2) | Favourites and recent items per user (Postgres or `console.*`, the developer says which and why); the command palette searches dashboards and charts by name across folders the user may read. |
| Templates (part 3) | A board can be saved as a template (`console.bi_template`: state as for a version, no data); "New dashboard" offers templates; starting from one creates an independent board. `dashboard:write`. |
| Reports (part 3) | A report is a board whose `kind` is `report`: one column, text blocks (markdown) interleaved with live chart tiles, printable. |
| Assistant (`AI-9`) | Part 1: `create_tab`, `rename_tab`, `move_charts_to_tab`, `delete_tab` (approval, as deleting); part 3: `list_templates`, `create_dashboard_from_template`, `save_as_template`. All in `src/features/copilot/capabilities.ts`; `tool_schemas.json` regenerated; tool count pin updated. |

**How the design works (what the reviewer should check first)**

- A deleted board or chart keeps its whole row with `is_deleted = 2`. Every read that asks for `is_deleted = 0` (all of them) leaves it out without knowing the trash exists: a path someone forgets cannot leak a deleted item. `deleted_at`, `deleted_by`, and for a chart `deleted_with` (the board whose delete took it) are extra columns. Plan said "sets a `deleted_at`": that is true, plus the state `2`, which is the safety property. Restore copies the row back with `INSERT ... SELECT`.
- A board in the personal space carries its owner's principal id in `bi_board.owner_id`; a chart is visible when its board is (one sub-select, `Viewer::chart_clause`). `lakehouse_bi::access::Viewer` is a required argument of `list_boards`, `get_board` and `list_stored_charts`, so a new read path does not compile without saying who is reading (`Viewer::system()` for the server itself, `anonymous()` for embeds, public links and alert digests).
- Writes: `boards_update`, `boards_delete`, `specs_create/update/delete`, the assistant's `create_chart/update_chart/delete_chart` and the tab tools first check the board or chart is live and visible, and answer with the same sentence as for an id that never existed. Before this, a layout save for a deleted board would have written a blank live row over its trash entry.
- Version revert re-checks the stored state against today's rules before any write (tabs, tile tabs, filters, phone layout, refresh, parameter controls, and every chart rebuilt by `spec_from_input` and run once). The first failure is a 422 whose sentence names the chart and why, and nothing is written (tested). Only then: charts written, charts added since moved to the trash, the content written back in ONE board save that carries the live public link, embed state, folder and owner, then a new version.

**Deviations and decisions for the planner**

1. Trash is `is_deleted = 2` plus `deleted_at`, not `deleted_at` alone (above).
2. Version 1 of a dashboard is written when it is created or duplicated; a board that existed before this change has no history until its next change, and then "Created" is the label of its first version. The built-in dashboard keeps no history (its tiles are code; "Version history" is not offered, the route answers an empty list, revert is a 400).
3. Going back moves charts added since to the trash and does not bring back charts deleted since (the feature page's limit: "charts deleted outright come back only from the trash"); the answer and the toast say how many of each. A chart restored from the trash returns to its board; its tile is where it was unless a layout save happened while it was deleted, in which case the page places it.
4. A private dashboard cannot be shared or embedded; a shared one cannot be moved into the space until sharing is off. An administrator can see and edit another user's draft, can move it out, but files only into their own space; duplicating someone else's draft gives the administrator a draft of their own.
5. A delete that is blocked by a use you cannot see says "a dashboard you cannot see" and never names it (metrics, segments, parameters, SQL sources, calculated fields). The count of hidden uses is not given.
6. The trash lists a dashboard with its charts as one entry; a chart deleted on its own is its own entry. Restoring a chart whose dashboard is in the trash brings it back with the dashboard, and one whose dashboard is gone leaves it on no dashboard (kept with the removed dashboard's id; the owner restriction survives the removal, tested).
7. Restore does not re-check the chart against today's rules (a chart whose mart was dropped in the meantime comes back and shows its tile error, like any chart whose mart is gone). Only the version revert re-validates, as specified.
8. The sweep runs in the API process every hour (the shape of `spawn_auth_cleanup`), on every replica; the removal is a tombstone insert, idempotent. It is not a Dagster schedule.
9. `delete_chart` and `delete_board` no longer wipe content: the old tombstone made the data unrecoverable at once; the trash keeps the spec for 30 days. Rows of a purged item are tombstoned like every other `console.bi_*` delete (content wiped); old parts disappear when `ClickHouse` merges them.
10. The version number is `max + 1`; two simultaneous saves of one board can write the same number and one version is lost. Saves of one board are rare and sequential in practice; stated, not engineered around.

## 1. Decisions

- **D1. The name is "AI Copilot", every time the interface names the assistant.** It is never
  "Copilot" alone, never "the Copilot" or "the copilot", and never "the assistant". It is used
  as a proper name, without an article: "ask AI Copilot", "AI Copilot can be wrong", "started
  from the console, AI Copilot or the API". (Product owner, 2026-11-02; the article rule is
  *(planner default)*.)
- **D2. "The assistant" is renamed too.** The owner's decision says "one name". The catalog
  meanings, the metrics line and Query Studio's SQL help are the same assistant (module AI
  Copilot, `AI-12`, `AI-16`), so they say "AI Copilot". *(planner default)*. The alternative is
  to keep "the assistant" as a common noun. The owner can say so at review, and then T2's
  "assistant" rows are dropped.
- **D3. Only user-visible text changes.** These do not change:
  - identifiers, routes (`/copilot`, `/copilot/history`), `localStorage` keys
    (`copilot-dock-pos`, …) and query keys;
  - the `emp-copilot` id and the `"copilot"` value of `principal_kind`/`trigger`;
  - code comments, log lines (`ai/audit.rs:293`, `:315`) and the scanner's fixture line in
    `tests/sec11_guard.rs:563`.

  Model-facing text is out as well: the tool description in `registry.rs:1436` is read by the
  model, not the user. Changing it would force `tests/fixtures/tool_schemas.json` to be
  regenerated for no user benefit.
- **D4. The unavailable texts become one sentence: "AI Copilot is unavailable."**
  - The API's `error` field (`ai/mod.rs:1508`) is already that; only the full stop is added if
    the console shows the field as a sentence. Check first: `chatErrorText` shows `detail`
    before `error`.
  - The headless run step (`agents.rs:1221`) becomes `"AI Copilot is unavailable. {ref}"`.
  - The console's fallback (`use-copilot.ts:72`) becomes "AI Copilot couldn't answer. Try
    again."
  - The cut-off and empty answers (`:382`, `:397`) become "AI Copilot's answer was cut off. Try
    again." and "AI Copilot didn't return an answer."
- **D5. The employee row is renamed by a migration.** The next free number when building:
  `0118` at `9c066426`, but `SEC-57` also adds one, so whichever merges second renumbers.
  - `UPDATE agent_employee SET name = 'AI Copilot' WHERE id = 'emp-copilot' AND name =
    'Copilot (interactive)' AND NOT EXISTS (SELECT 1 FROM agent_employee WHERE name =
    'AI Copilot')`. The name is `UNIQUE` (`0017_agents.sql:33`), so a customer's own employee
    named "AI Copilot" must not make the API fail to start. In that case the row keeps its old
    name, and the header says so.
  - `UPDATE approval_item SET employee_name = 'AI Copilot' WHERE employee_id = 'emp-copilot'
    AND employee_name = 'Copilot (interactive)'`, so Approvals shows one name for old and new
    rows. `employee_name` is a denormalized label (`agents.rs:1440-1446`), not evidence.
  - `audit_event` is immutable and is not touched.
  - `COPILOT_EMPLOYEE_NAME` becomes `"AI Copilot"`.

  *(planner default: "AI Copilot", not "AI Copilot (interactive)"; the employee page's
  description already says it is the interactive chat.)*
- **D6. Tests that assert a string are updated to the new string, never loosened (rule 2).** A
  `toBe` stays a `toBe`, and a regex stays anchored. `chat-messages.test.tsx:33` asserts that no
  name is shown beside an answer. It gains a second assertion,
  `queryByText("AI Copilot")` is null, so the rename cannot bring the label back unnoticed.
- **D7. The owner's QA-1 sentence is aligned in the docs, not built here.**
  `copilot-chat.md:230` says the console shows "The assistant isn't available, ask your admin."
  with no model endpoint. With D1 the sentence reads "AI Copilot isn't available. Ask your
  admin." The page is updated. Making the console show exactly that sentence (today it shows the
  API's `detail` and a reference, `use-copilot.ts:72`) is an `AI-18` gap and is not built
  here. *(planner default)*

## T1 `OPS-9`: the per-table maintenance route shows a Bronze table's last run

- **Gap.** The maintenance job records a Bronze table under its qualified
  name (`bronze.<table>`); `A/routes/lakehouse.rs:347`
  `maintenance_verb_run_query` and `A/routes/governance.rs:484`
  `maintenance_run_query` filter on the bare name from the URL
  (`GET /api/lakehouse/tables/{ns}/{table}/maintenance`), so a Bronze table
  never shows its last run. The aggregate Governance view is right.
- **Decision.** Find where the job writes the name (Dagster maintenance
  asset; grep the table name of the run log) and build exactly that name
  from `{ns}` and `{table}` in one helper both queries use (rule 4); keep
  the value bound as a literal (the existing escaping tests at
  `lakehouse.rs:1378` and `governance.rs:1876-1893` must still hold). If a
  namespace other than Bronze records a bare name, the helper says so.
- **Check.** Unit tests for the helper (Bronze qualified, the other
  namespace as recorded), the existing SQL-literal tests, and a route test
  if the route has one today. Each fails without the fix.

## T2 `OPS-4`: fail loudly when the application database cannot be used

- **Today.** `A/main.rs:102-118` logs a migration failure and keeps
  serving, on purpose (an unreachable Postgres must not take down the
  Phase 1 routes). PRs #106 and #199 showed the cost: a database whose
  `_sqlx_migrations` disagrees with the code stops sqlx at the first
  mismatch, the API starts anyway, and every newer route answers 500.
- **Decisions (planner).**
  1. Reachable database, migration **fails** (version mismatch, a failed
     statement, a checksum change): the API refuses to start, exits non-zero,
     and logs the migration error and a fixed line saying the schema is not
     at this build's version (fail closed, principle 3). Compose restarts it;
     the log says why every time.
  2. Database **unreachable** at start: keep today's degrade (Phase 1 routes
     serve, Phase 2 answer 503), but loudly: an `error!` at start and again
     on a fixed interval (say every 60 s, a constant with its reason) until
     a connection succeeds, and the health route reports the database as
     unavailable rather than healthy. Read what `/health` (or `/healthz`)
     returns today and extend it; do not add a second health route.
  3. Say both in `main.rs`'s comment (replacing the "logged rather than
     fatal" paragraph) and in `docs/OPERATIONS.md`.
- **Check.** A test that a failing migration makes the start-up function
  return an error (factor the start-up step so it is testable without
  starting the server; no `process::exit` inside library code); a test that
  the health body names the database as unavailable when there is no pool.
  Each fails without the fix.

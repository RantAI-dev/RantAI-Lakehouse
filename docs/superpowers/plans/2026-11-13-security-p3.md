## 1. Decisions

- **D1. One task per commit, in the order of section 2.** `GOV-15` first (security), then
  `DATA-61`, then the documents. Each commit body cites `GOV-15 (GOV-12 plan, section 4)` or
  `DATA-61 (#501 review, round 1 (R4))`. Each fix site carries a short comment that starts the
  same way (rule 13), for example `// GOV-15 (GOV-12 plan, section 4): …`.
- **D2. No new guard** (rule 4). The helpers used: `catalog_tenant_refusal`
  (`routes/catalog.rs:210-236`), `table_access_for` (`routes/catalog.rs:3200-3205`),
  `TableAccess::allows` and `TableAccess::allows_key` (`src/table_access.rs:76-101`),
  `ensure_rule_table` (`quality.rs:978-1045`), `FILE_INGEST_JOB` (`uploads.rs:260`),
  `enforce_run_id_pipeline_scope` (`pipelines.rs:3888`). The one change to a helper is T1: the
  two steps "catalog tenant rule, then the role's table access" that `ensure_rule_table` runs
  inline (`quality.rs:1006-1021`) move into one function, `quality_table_access`, which
  `ensure_rule_table` then calls; every route of this plan calls it too. No route repeats
  `catalog_tenant_refusal` and `table_access_for` by hand. The refusal sentence of
  `ensure_rule_table` (`:985-990`) becomes one function, `unreadable_table`, so the schedules
  give the same sentence without a second literal.
- **D3. "Outside the tenant" answers 403 on every route of this plan**, the body the run
  gives: `ApiError::PermissionDenied(reason)` with the reason `catalog_tenant_refusal` returns.
  The same answer whatever the rule, the incident, the table, and whether it exists.
- **D4. The tenant gate is the first thing each handler does**, before the body is read and
  before anything is looked up, on: the edit, the delete, the rule list, setting and resetting
  a schedule, resolving an incident. So a caller outside the tenant learns nothing, not even
  whether a rule id or incident id exists. This differs on purpose from the run, where
  `GOV-12` D6 looks the rule up first (kept: `tests/route_auth.rs:2651-2685` expects 404 for an
  unknown rule from a caller with no tenant). The run is not changed.
- **D5. The role's table access applies on every route, and what a hidden thing answers.**

  | Route | Table checked | Hidden from the caller's role | Table not there |
  | --- | --- | --- | --- |
  | `PUT /api/governance/quality/{id}`, table kept | the rule's stored `asset` | 404 `Quality rule not found` | not checked (as today, `DATA-54`: a rule on a dropped table can still be edited) |
  | `PUT /api/governance/quality/{id}`, table changed | the stored `asset` **and** the new one | stored hidden: 404 as above; new hidden: 400, `ensure_rule_table` unchanged | new table: 400, `ensure_rule_table` unchanged |
  | `DELETE /api/governance/quality/{id}` | the rule's stored `asset` | 404 `Quality rule not found` | not checked (a seeded rule on a table that never existed can still be removed) |
  | `GET /api/governance/quality` | each row's `asset` | the row is left out | not checked |
  | `PUT`/`DELETE …/quality/schedules/{asset}` | the path's table key | 400, the `unreadable_table` sentence | not checked (as today) |
  | `POST …/incidents/{id}/resolve` | the incident's `asset` | 404 `Quality incident not found` | not checked |

  Reasons. A rule or an incident on a hidden table is not on the caller's list (D6), so for
  that caller it does not exist: the answer is the one an unknown id gets, the same status and
  the same body. The schedule names a table, not a rule, so it gets the sentence a rule on that
  table gets (`DATA-54`'s create). None of these answers depends on whether the table exists:
  where existence is not checked it cannot leak, and where it is (`ensure_rule_table` on a
  changed table) the access step runs first. A principal with no roles, or with `*:*`, is
  `TableAccess::All` and is not narrowed (`table_access.rs:7-13`).
- **D6. The rule list hides rows the way the catalog list hides tables.** The catalog list
  drops what `TableAccess` hides (`catalog::retain_visible`, `routes/catalog.rs:3252-3257`,
  called at `:306`, `:343`, `:525`): nothing at all when the access is `All`, otherwise only
  rows whose table key the access allows, and a row whose table cannot be named is hidden
  (fail closed, `GOV-7` D6). `retain_visible` itself cannot be called: it reads a row's
  `tableKey` or a dotted `id`, and a quality row's key is its `asset` (an authored rule's `id`
  is a UUID, an observed row's is `q-<n>`). So the list applies the same rule to `asset`: keep
  everything when `access.is_all()`; otherwise keep a row only when its `asset`, trimmed, is
  allowed by `access.allows_key`. `allows_key` already hides a name with no schema from a
  narrowed principal (`table_access.rs:96-101`). Consequence, accepted: an observed verdict
  whose `tabel` is a bare name (no zone) is hidden from a narrowed person.
- **D7. The assistant reads the rule list as the person.** `list_quality_rules` passes the
  person (`Option<&Principal>`) and an empty header map to the same function the route calls,
  as `draft_quality_rule` does (`routes/ai/tools/governance.rs:158-184`). No tool, schema or
  `tests/fixtures/tool_schemas.json` change (assistant parity applies to dashboards; this is
  noted for the AI team only). The other governance tools (`get_audit_history`, …) pass no
  person and are unchanged. A tool call with no principal is not narrowed, the convention
  `ensure_rule_table` already has (`quality.rs:1009-1010`).
- **D8. Nothing is written by a refusal.** Every refusal of this plan comes before the store
  call and before any `ClickHouse` call of the handler: no row changes, no `audit_event`, no
  `ALTER TABLE console.quality_run DELETE`, no incident resolved, no schedule stored. For the
  rule list, a refused caller causes no `ClickHouse` query at all.
- **D9. The cost, accepted.** Each gated write route reads the tenant count and the caller's
  roles once more (two small Postgres queries). A rewrite that changes the table reads them
  twice (once in the gate, once inside `ensure_rule_table`), which is not restructured.
  Resolving an incident reads the incident once before the update (a new store read, T5).
- **D10. The console needs no change for `GOV-15`.** The Data Quality page lists what
  `GET /api/governance/quality` returns (`src/features/governance/data-quality-page.tsx:46`,
  `listQuality`); a narrowed person sees fewer rules and the page's filters and counts work on
  that list. A person outside the tenant already gets the page's error state for the incident
  list beside it; the rule list now answers the same way. The page still shows the incident
  and schedule tabs unfiltered by role (section 4).
- **D11. `DATA-61`: a re-run of a `file_ingest_job` run is refused, with one fixed sentence,
  before anything is launched.** Chosen over routing it through the upload's checks. Reasons:
  the run's config names an upload, a table and options that may all have changed since; doing
  it right means mapping the run back to its upload row, re-reading it, `ensure_table_free`,
  the `DATA-55` refusal, the claim and the launch, which is `POST /api/uploads/{id}/ingest`
  over again, a second copy of the upload route (rule 4). The upload page already does all of
  that from the upload's own row. Refusing is safe (principle 3) and costs nothing anyone uses:
  the upload's own "Load" / "Try again" is the way to load a file again.
  - Status `409`, body `{"error": FILE_LOAD_NOT_RERUN}` with the constant
    `FILE_LOAD_NOT_RERUN` (in `pipelines.rs`), exactly:
    `A file load is not re-run from Pipelines. Load the file again from the "Uploaded files" tab of Sources, which checks the table first.`
  - It applies to every retry body: empty (all steps), `fromFailure` and `selected`.
  - It comes **after** the scope check (a run out of the caller's scope, or unknown, still
    answers 404 as today) and **before** the body is parsed and before any launch.
  - The job name comes from the scope check, which already reads it
    (`pipeline_run_pipeline_name`, `pipelines.rs:3894`): `enforce_run_id_pipeline_scope`
    returns it instead of `()`. Its three other callers (`:1391`, `:1579`, `:3981`) use
    `if let Err(rejection) = …` and are not edited. No second orchestrator call.
  - Any other job's re-run is unchanged, including `ingest_job` (a connector's load; see
    section 4).
- **D12. `DATA-61` changes no console file.** The run inspector shows "Re-run" for a failed or
  cancelled run (`src/features/pipelines/run-inspector.tsx:216`); pressing it on a file load
  shows the toast "The re-run could not be launched" with the API's sentence as its
  description (`withNotify` → `notifyError`, `src/lib/notify.ts:46-79`). Hiding the button for
  a file load is an open question (end of section 4). The assistant's `retry_pipeline_run`
  gets the same refusal as its tool result; no tool or schema change.
- **D13. No route, `POLICY_TABLE` row or migration changes.** `tests/route_auth.rs` is not
  edited; it is still run (section 3a). The highest migration is not touched.

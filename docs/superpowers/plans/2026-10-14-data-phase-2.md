## Rules for the whole phase

- **One branch, one PR.** Everything lands on `feat/data-12-certification-governed-tags`;
  #106 is merged once, at the end, by the planner (step 6 of `AGENTS.md`).
  The developer never opens or merges it.
- **Merge `main` into the branch before each item starts and whenever `main`
  moved meaningfully.** Conflicts are resolved hunk by hunk (rule 9); after a
  merge that touched code, the scoped compile check runs before the merge commit
  (`cargo check -p lakehouse-api --all-targets --locked`, `bun run typecheck`).
- **Migration numbers.** Whoever merges second renumbers. On this branch the
  next free number is `0074` (`0072` is the part-1 certification migration and
  `0073` is governed tags, both renumbered after the merge of `main` at
  `cacf7991` because main's `0070_reporting_settings.sql` and
  `0071_pipeline_definition_version_tenant.sql` took `0070`/`0071`; main's
  last is `0071`). After each merge
  from `main`, check the **whole overlap for colliding numbers**, not just the
  top of the range — `ls rust/migrations | cut -c1-4 | sort | uniq -d` must
  print nothing — and renumber the branch's own unmerged migrations above
  main's last before anything else.
- **Per-commit checks stay scoped** to the languages the commit touched; the
  full verification block runs once per item before its handoff, and once more
  by the reviewer before merge. Shared target dir:
  `CARGO_TARGET_DIR=/home/hv/.cache/lakehouse-catalog-target`, and from
  2026-10-14 every Rust build in this phase sets `CARGO_INCREMENTAL=0`
  (the incremental caches were what filled the disk; see the status log).
- **Assistant parity (part 3 only).** The chart builder is a dashboards
  feature: its plan names the assistant change (`describe_mart` answers say
  when a mart is deprecated; regenerate
  `rust/crates/lakehouse-api/tests/fixtures/tool_schemas.json`), and the AI
  team reviews that part of the plan and of the diff.
- **Known red check.** `gitleaks` (working tree and full history) is red on
  `main` and on this PR; it did not start here and has backlog item `SEC-27`.
  It does not block items, and it is named again at merge time. A PR that
  touches dependencies still cannot merge while it is red (step 6).
- **Reviews.** The planner reviews after each item's handoff (findings tagged
  `BLOCKER`/`SHOULD-FIX` in the item's plan), not only at the end; the owner
  runs the item's acceptance checklist on a running console before the item
  counts as accepted.

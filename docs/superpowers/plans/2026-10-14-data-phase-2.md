## Rules for the whole phase

- **One branch, one PR.** Everything lands on `feat/data-12-certification-governed-tags`;
  #106 is merged once, at the end, by the planner (step 6 of `AGENTS.md`).
  The developer never opens or merges it.
- **Merge `main` into the branch before each item starts and whenever `main`
  moved meaningfully.** Conflicts are resolved hunk by hunk (rule 9); after a
  merge that touched code, the scoped compile check runs before the merge commit
  (`cargo check -p lakehouse-api --all-targets --locked`, `bun run typecheck`).
- **Migration numbers.** Whoever merges second renumbers. On this branch the
  next free number is `0074` (`0072` is the part-1 certification migration and
  `0073` is governed tags, both renumbered after the merge of `main` at
  `cacf7991` because main's `0070_reporting_settings.sql` and
  `0071_pipeline_definition_version_tenant.sql` took `0070`/`0071`; main's
  last is `0071`). Update 2026-10-16: main took `0072`/`0073` in #144, so the
  two became `0082_asset_certification.sql` and `0083_governed_tags.sql`.
  After each merge
  from `main`, check the **whole overlap for colliding numbers**, not just the
  top of the range — `ls rust/migrations | cut -c1-4 | sort | uniq -d` must
  print nothing — and renumber the branch's own unmerged migrations above
  main's last before anything else.
- **Per-commit checks stay scoped** to the languages the commit touched; the
  full verification block runs once per item before its handoff, and once more
  by the reviewer before merge. Shared target dir:
  `CARGO_TARGET_DIR=/home/hv/.cache/lakehouse-catalog-target`, and from
  2026-10-14 every Rust build in this phase sets `CARGO_INCREMENTAL=0`
  (the incremental caches were what filled the disk; see the status log).
- **Assistant parity (part 3 only).** The chart builder is a dashboards
  feature: its plan names the assistant change (`describe_mart` answers say
  when a mart is deprecated; regenerate
  `rust/crates/lakehouse-api/tests/fixtures/tool_schemas.json`), and the AI
  team reviews that part of the plan and of the diff.
- **Known red check.** `gitleaks` (working tree and full history) is red on
  `main` and on this PR; it did not start here and has backlog item `SEC-27`.
  It does not block items, and it is named again at merge time. A PR that
  touches dependencies still cannot merge while it is red (step 6).
- **Reviews.** The planner reviews after each item's handoff (findings tagged
  `BLOCKER`/`SHOULD-FIX` in the item's plan), not only at the end; the owner
  runs the item's acceptance checklist on a running console before the item
  counts as accepted.

#### BLOCKER

1. **DATA-12: tag-key writes have no tenant gate.**
   `routes/governance.rs` `create_tag_key`, `update_tag_key`,
   `delete_tag_key` never call `catalog_tenant_refusal`, and
   `0083_governed_tags.sql` has no tenant column. On a multi-tenant install a
   `governance:write` holder outside the catalog tenant can add keys that
   show in the catalog owner's About editor, widen a key's allowed values, or
   delete unused keys. The annotation and certification writes on the same
   catalog are gated (`catalog.rs` ~2997, ~3243). Fix: the same gate on all
   three writes (and the GET if keys count as catalog metadata); a test for a
   caller outside the catalog tenant.

2. **DATA-12: a spec target is reported as met but is not built.** The spec
   says tags show "in search results, the Data Explorer list, the asset page,
   the chart builder's table picker and Query Studio". `GET
   /api/dashboard/fields` and the estimate's `sourceMarks` carry only the
   certification marks; `chart-builder.tsx` and
   `query-transparency-panel.tsx` show no tags. The parts 2–3 plan lists the
   target, no task builds it, and the PR body says "Met, except tag
   inheritance". AGENTS: a target that cannot be met is reported, not
   quietly lowered. Fix: build it, or record it as not met with the owner's
   decision and a backlog item, and correct the PR body.

3. **DATA-14: runs that load nothing open false volume anomalies and send
   alerts (principle 2).** `routes/quality_load.rs` `connector_success`
   starts the follow-up whenever `connector_run_event` returns `Ok`,
   including `skipped("a paused run loads nothing")`
   (`load_alerts.rs` ~428); `connector_tables` takes every
   `source_objects[].target` even for a one-table refresh or clear. A learned
   append-only table then records a 0-row load, `0 < 0.5 × median` opens a
   `volume_anomaly` incident and alerts. "Refresh table A" on a five-table
   connector gives four false incidents and four alerts; the false loads also
   reset the freshness clock. Fix: follow up only when the event counted a
   load; a one-table run follows up only its `object`; skip `clear`; tests
   for a paused and a one-table run.

4. **DATA-15: a granter can give a permission they do not hold.**
   `routes/catalog_grants.rs` `create` checks `held.has(permission)` on the
   grantee only, never `principal.has(permission)`. A custom role with
   `access:approve` but not `catalog:write` grants `catalog:write` to a
   second account it controls. Fix: a fixed 403 unless the granter holds
   it; a test. (`decide_access_request` on `main` has the same gap, but there
   the grantee had to ask first; record it as a follow-up.)

5. **DATA-15: a grant can go to a user outside the catalog tenant.**
   `find_user_by_email` searches all of `app_user`; `create` never checks the
   grantee's tenants (the principal loaded for `held` has them). On a
   multi-tenant install that user gets a global 30-day `query:read`, and
   Query Studio's run path has no tenant gate. Fix: the grantee must be a
   member of the catalog tenant when more than one tenant exists; a test.

6. **DATA-15: the usage card shows literals it says are hidden.**
   `sql_rewrite.rs` masks only what the ClickHouse parser reads as a
   literal; a double-quoted or backticked string is an identifier and is
   printed back. `frequent_queries` is built from every status
   (`catalog_governance.rs`; only latency filters to `completed`), so a
   rejected `WHERE email = "jane@corp.example"` is shown verbatim to every
   `catalog:read` user. Fix: count only completed queries, and drop (or
   mask) a query with a quoted identifier that is not a known table or
   column; a test with that query.

7. **DATA-13: the mapper stores a guess as a complete mapping
   (principle 2).** `sql_lineage.rs` ~789–807: with two tables in `FROM` and
   one table's columns unreadable, that table is dropped from the candidates
   and an unqualified column is mapped to the other one. The module doc
   promises this case is partial. Fix: an unchecked table makes the column
   ambiguous (partial, with the reason); a unit test "one table known, one
   unknown".

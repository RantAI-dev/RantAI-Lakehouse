# CI that is red for reasons no PR caused

Plan by the planner, 2026-10-14. Base: `main` at `112cd8b`. The product owner
asked: "why does CI keep failing; is there a root cause that is not the
authors' fault? Fix it first, so the PRs can go green."

## What was found

Every check on `main` passes except the two gitleaks jobs. Across recent PR
runs, these failures were not caused by the PR that showed them:

| # | Check | Root cause | Evidence |
| --- | --- | --- | --- |
| F1 | `gitleaks (working tree)` | `dagster/dispar_orchestrate/test_schema_observer.py:26` holds a test token literal that matches `generic-api-key` (added with `SRC-8`, #101) | gitleaks log on `main`, finding 1 of 8 |
| F2 | `gitleaks (working tree)` | `.env.staging` holds seven staging tokens and secrets in clear (`SEC-13`) | gitleaks log on `main`, findings 2 to 8 |
| F3 | `Rust · SRC-17 alert delivery` | `ops/g6/src17_alert_delivery_test.py` starts before the Dagster code location is loaded; the run launch gets `Dagster HTTP 500` while the daemon logs "Could not reach user code server". | F4 | `ci-required` on `main` pushes | `concurrency: cancel-in-progress: true` applies to pushes to `main` too, so two quick pushes cancel the first run and its `ci-required` reads as failed (`200b7d6`, `aa196f6`) | check runs on those commits |
| F5 | `Frontend` on dependabot npm PRs | `.github/dependabot.yml` uses the `npm` ecosystem, so dependabot updates `package.json` (and reads the stale `package-lock.json`, `REL-3`) but not `bun.lock`; CI's `bun install --frozen-lockfile` then fails | #39 job log: "lockfile had changes, but lockfile is frozen" |

| F7 | `gitleaks (full git history)` | A real key in old commits (`SEC-1`) plus every finding above, still in history. It is red by design until the key is confirmed rotated and history is rewritten or the rotated findings are baselined | `security.yml` comments, `docs/CI.md` |

## Decisions

1. F1, F3, F4, F5 are fixed in one PR by a developer agent (not the planner:
   `ops/` and `dagster/` are product code, `AGENTS.md`).
2. F1 is fixed by changing the test literal so it no longer looks like a key,
   **not** by an allowlist entry (rule 2: never weaken an allowlist to get
   green).
3. F3 reuses the readiness poll the other gates already have (rule 4: grep for
   the existing helper before writing one). No test is skipped or loosened.
4. F4: `cancel-in-progress` only for pull requests, so every push to `main`
   gets a full run.
5. F5: switch the ecosystem to `bun` and delete `package-lock.json`, which is
   also `REL-3`. Existing dependabot npm PRs are left for dependabot to
   recreate.
6. F2 is a second, separate PR because it needs the product owner to add eight
   `STAGING_*` repository secrets first. It is the `SEC-13` part of #105
   (ce2a069), taken out so it does not wait for #105, merged with the lines
   added to `.env.staging` since. Rotating the values stays with the product
   owner (`SEC-13`).
7. F7 is not touched here. It needs the owner's `SEC-1` decision.

## Review (planner)

- **F3, the planner's premise was wrong, and the developer was right to stop.**
  - The gate already polled `repositoriesOrError` for `ingest_job`.
  - The job's `up` step already starts every service the runner depends on.
  - The `up` and `run` steps use the same files and profiles, so the restart of the code server in the #127 run is still **unexplained**.
  - `--no-deps` is a safeguard, not a proven fix. It keeps `compose run` from touching services `up` already started. It is safe because `up` starts the runner's whole dependency set.
  - The new wait for `file_ingest_job` closes a real gap: the gate launched that job without waiting for it.
  - If F3 recurs, re-open it with the new logs.
- **F1**: the literal is changed, and no allowlist entry was added. Correct.
- **F4, F5**: correct.
  - Nothing reads `package-lock.json`; `.gitignore` already lists it.
  - Dependabot's `bun` ecosystem shows itself on dependabot's next run (not verified).
- **F2**: correct.
  - The secrets are passed through `env:`, not interpolated into the script.
  - A missing secret fails the deploy and names it.
  - Do **not** merge until the product owner has added the eight `STAGING_*` secrets.
- No `BLOCKER`.

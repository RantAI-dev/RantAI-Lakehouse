## 1. Decisions already made (do not re-ask, do not change)

| Decision | Choice |
| --- | --- |
| Metric | A new `console.bi_metric` table (created like the other BI tables): id, `name` (an identifier, unique in the deployment), `label`, `description` (at most 500 characters), source (a mart or a SQL source), `formula` (formula language, must check as aggregate level over that source; table calculations and parameters with no default are refused), `filters` (a list of `FilterDef` and segment references on that source), optional `timeColumn` (a date or timestamp column of the source) and default `grain`, optional `format` hint, created by, updated at. |
| Segment | A new `console.bi_segment` table: id, `name` (identifier, unique per source), `label`, source, `filters` (a list of `FilterDef`). Usable wherever a chart filter is (`BI-6`) as `{ "segment": <name> }`, and inside a metric's filters. |
| Routes and permission | `/api/dashboard/metrics` and `/api/dashboard/segments`: `GET` with `dashboard:read`; `POST`, `PUT`, `DELETE` with the new `metric:write`, introduced as `settings:write` was (policy module doc, seed migration with the next free number checked against `origin/main` and open PRs, no seed grant beyond what `*:*` already gives unless the policy doc says otherwise). `GET /api/dashboard/metrics/{id}/usage` lists the charts, KPIs, alerts and dashboards that use it, by title. A validate route checks a metric definition without saving. All in `POLICY_TABLE` and `route_auth`. Delete in use is 409 with the usage list. `name` and source are immutable. |
| A metric's filters | Applied to the metric's number only: each aggregate in the compiled formula takes the filter as its condition (the engine's conditional form of that aggregate), so a filtered metric and an unfiltered measure can share one statement and one grouping. A formula whose aggregate has no conditional form is refused at save with a positioned message. |
| Use in a chart | A measure may be `{ "metric": <name> }` on a chart whose source is the metric's source (with `BI-7` joins: the base table). It behaves as an aggregate-level field: no chart aggregation, allowed where aggregate fields are. Charts store the name, not a copy, and are rebuilt at read time, so a changed metric reaches every chart at once. A missing metric is the tile's plain error, never a silent fallback. |
| KPI and comparisons | A `kpi` may take `{ "metric": <name> }` as its measure. For a metric with a `timeColumn`, the KPI's `compare` defaults to that column and grain, and gains `{ "kind": "last_year" }` beside `previous` (same period one year earlier, by calendar shift as `SamePeriodLastYear` does). |
| Alerts | An alert rule can watch a metric by name with the comparison operators it already has, evaluated through the same builder path as a KPI tile, with the rule owner's permissions as today's rules do. If today's alert rules cannot run a builder statement without a larger redesign of the alerts crate, stop and report the options instead of building around it. |
| Built-in cards | Unchanged. |
| Assistant (`AI-7`) | Tools: `list_metrics` (names, labels, descriptions, sources), `describe_metric`, `query_metric` (the metric's value, optionally grouped by one column or a time grain and filtered, through the same builder path and the caller's permissions), `create_metric` / `update_metric` (low-risk writes, `metric:write`), `delete_metric` (approval). The system prompt's dashboard section tells the model to look for a matching metric before writing SQL, to name the metric it used, and to say when none matched. All tools named in `src/features/copilot/capabilities.ts`; `tool_schemas.json` regenerated, tool count assertion updated. |
| Export | `chart_def_fields` lists the `{ "metric": … }` form. |

#### How it is built (what the decision table left open)

1. **A metric is an aggregate field with a home and a condition.** Metrics and segments are loaded with the calculated fields into the `FieldCatalog` every read already carries, as entries of level `metric` / `segment` (body as JSON in `formula`, as a value group does). So the dashboard, the embed and public read, the preview, the questions of a combined chart and the digest all see them with no new argument; the routes that edit calculated fields keep `list_fields` and never see them. A segment a metric names is expanded when the entry is made; one that is gone leaves the entry with an `error`.
2. **Filters never get dropped.** `condition_of` fails the metric when a filter does not apply to the source; the condition is the ordinary predicate builder's output (escaped literals), and every aggregate is compiled in its `-If` form (`sumIf(x, cond)`, `countIf(cond)`, `quantileExactIf(p)(x, cond)`, `SumIf(x, p)` becomes `sumIf(x, (p) AND (cond))`). No aggregate of the catalog lacks a conditional form, so "refused at save for an aggregate with none" never fires; a table calculation, `Fixed` or a non-aggregate is refused with a positioned message.
3. **A missing metric or segment is the tile's error.** `stored_chart_sql` (the one function every tile goes through) refuses a chart whose metric or segment is missing, on another source, or no longer checks out ("this chart uses a metric or segment that is missing or no longer checks out"), instead of the builder's old fallback to the statement saved with the chart. If the metric tables cannot be read, `with_metrics` leaves the metrics out (logged), so only the tiles that name one fail.
4. **Engine finding, fixed.** `SELECT sumIf(visitors, …) AS m, round(sum(visitors)) AS visitors` is rejected by the engine (an alias is preferred to a column inside an aggregate: "Aggregate function sum(visitors) is found inside another aggregate function"), which is exactly the "metric beside an unfiltered measure" case of AC2. A statement with a metric now ends `SETTINGS prefer_column_name_to_alias = 1` (only when a metric is in it; a chart with a calculated aggregate keeps its statement byte for byte).
5. **KPI comparison.** A comparing KPI may take a metric (`takes_aggregate_measure`); the trend statement uses the metric's aggregate as the per-period number and carries the columns it reads. `{ "kind": "last_year" }` returns enough periods with data to reach a year back (day 400, week 60, month 14, quarter 6, year 2); the console finds the bucket a year earlier (a calendar year, 52 weeks for a week) and also shows the change against the previous period, so one card shows both comparisons (AC3). With no date column or period on the comparison, the metric's are used; the stored chart keeps the comparison as written.
6. **Usage.** `GET /api/dashboard/metrics/{id}/usage` lists charts (id, title, kind, board), the dashboards by name, and `alerts` (empty until T3). The 409 on delete names them. The "change shows usage" confirmation is the console's: `PUT` itself applies at once, as the decision table says "changing a metric ... applies to all of them at once".
7. **Assistant.** `query_metric` builds the same synthetic chart (`value_chart`) and runs it with the *caller's* roles, placeholders and obligations (`routes::metrics::value_query`); without a principal it refuses. `list_metrics`, `describe_metric` and `query_metric` are in `ALWAYS` (offered on every turn) and in the Query Data capability of the console (so they work in Ask mode); the three writes are in the Dashboard Builder capability. The filters schema of the chart tools became `oneOf [segment reference, filter]` and the measures schema gained a fourth entry, `{ metric }`.

#### T3 — alerts on a metric: not built; options

Today's rule is `mart` + `measure` + `agg` and is evaluated by `current_value` (`SELECT agg(measure) FROM serving.mart` through the `SqlGate`), which runs as the fixed `EMBED_VIEWER_ROLE`. Two things differ from the plan's sentence "with the rule owner's permissions as today's rules do": a rule has **no owner**, and it is read as that fixed restricted viewer role, not as its author (so a metric alert would read what that role may read, which is fail-safe). A builder statement *can* be run by the alerts crate without redesign (it already depends on `lakehouse-bi` and loads the catalog for digests): add `metric: Option<String>` to the rule (+ an `ALTER TABLE ... ADD COLUMN`), and in `current_value` build `value_chart` over the metric's source (`system.columns` for the mart, `list_catalog_fields_for`), gate it and run it. The cost is the surface, not the crate: the rule type, its input and validation, the alerts route, the console's alert form and contract, the assistant's `create_alert_rule` schema and fixture, and the `alerts` list of the usage route. I did not build it. Options for the planner: (A) build it as described, accepting the fixed viewer role; (B) add an owner to rules first (a larger change: who evaluates, what happens when the owner loses a role); (C) leave it out and keep the sentence in the feature page's "what the user can do" (item 6) as not met.

### Fix handoff — BI-2 review fix (BLOCKER) R1 (developer, 2026-10-11, uncommitted, on top of the docs commit after `b18a5c1`)

**Cause.** The save path rebuilt the stored definition's measures from `(column, aggregate)` pairs (`stored_measures`, `MeasureList::from_pairs`), which forgets which entries are metrics. The saved chart then held `["total_visitors_demo", "office_visitors_demo"]` as plain names; the preview (which reads the request, still marked) worked, the dashboard (which rebuilds from the stored definition) did not, and the builder summed the metric names as columns (`round(sum(total_visitors_demo))`). A KPI worked only because `catalog.chart_uses` is true for any name that matches a catalog entry; the KPI's stored definition had lost the marker too (`vec![m].into()`), so it too was one step from the same failure.

**Fix at the root.** `MeasureList::keeping_metrics_of(from, replaced)` carries the marker across every place a list is rebuilt from pairs: `stored_measures` (the save), the KPI's one measure (`kpi_measure`), a layer's measures (`layers.rs`), a parameter's column switch (`params.rs`), and the switch probe at save (`store.rs`); a swapped entry loses it. Every other saved-tile path reads the stored definition through the same builder, so they inherit the fix: the dashboard, the embed and public reads (`stored_chart_sql`), a combined chart's questions, the preview, the records for a clicked value (they use the chart's filters, not its measures), the raw-table export and the YAML export (the YAML writes `measures` from the stored list, so it now prints `{ "metric": … }` instead of the bare name), and the alert digest (a mart tile runs the statement saved with the chart, built at save through the prepared relation, so it was never wrong).

**Charts already saved heal on the next read, without a re-save.** The marker is not in storage for them, but `named_metrics` now reads a plain measure whose name is no column, no calculated field, and is a metric of that chart's source as that metric. The demo tile `u_0a8c305e` therefore loads on the next dashboard read; saving it again would also store the marker. (A name that is a column keeps being the column.)

**Tests.** `store::tests::a_saved_chart_keeps_its_metric_measures_and_the_read_builds_the_formula` saves a chart with a metric and a plain measure, asserts the stored list is `[{metric}, "visitors"]`, builds the dashboard's statement (`sql_with_filters_report`, the function under `stored_chart_sql`) with the metric in the catalog and asserts `sum(visitors) AS total`, not `sum(total)`; then strips the marker (a chart saved before the fix) and asserts the same.

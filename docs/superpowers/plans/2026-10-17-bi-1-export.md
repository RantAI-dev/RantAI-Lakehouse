### Excel format for IDR, compact, 2 decimals

`lakehouse_bi::export_format::excel_number_format` for `{"style":"compact","currency":"IDR","decimals":2}` under the `id-ID` locale:

```
[>=1000000000]"Rp "#,##0.00,,," B";[>=1000000]"Rp "#,##0.00,," M";"Rp "#,##0.00
```

For 1,234,567 the second section applies (value divided by 10^6 by the two trailing commas): **`Rp 1.23 M`** with an English-regional Excel, **`Rp 1,23 M`** with an Indonesian-regional one, which is what the console shows. *Not verified in Excel*: there is no Excel or LibreOffice here; the string follows Excel's documented number-format rules, and the tests check that it is written to `xl/styles.xml` and the amount is a numeric cell (`<v>1234567</v>`). What Excel cannot express, written in the module doc: separators are always `.` and `,` in the file and the reader's regional settings choose what they see (the deployment locale only picks the currency symbol: `Rp` for `id-ID`, `IDR` for `en-US`, as `Intl` does); a number format has two conditions plus the rest, so compact has the tiers billions (`B`), millions (`M`) and everything below in full, never `K` or `T` (a value of 2.5 trillion shows `2,500.00 B`), and a negative number does not match a `>=` condition so it is shown in full; `number` with no decimals set and `auto` stay Excel `General` (no "at most 3 decimals" code without a dangling point); `percent` without decimals shows 2, `compact` 1, `scientific` 2. CSV "formatted" is the text the chart shows (`format_text`); `export_format_cases.jsonl` holds 340 `[locale, format, value, text]` lines produced by running the console's own `formatValue` under `bun`, and a unit test compares every one. A negative formatted CSV cell starts with an apostrophe, because it starts with `-` (the one neutralising rule).

### Deviations and judgement calls, for the reviewer

- **Engine format.** `query_stream` asks for `JSONCompactEachRowWithNamesAndTypes`, not `JSONEachRow`: an empty result still has its header (a file with no rows keeps its column names), a row is an ordered array, and the types line tells a quoted `Int64` from text.
- **CSV through a file.** The plan says CSV is written to the response as rows arrive. `X-Export-Rows` / `X-Export-Cut` and the audit record both need the counts before the file is sent (D8), and the counts are known only at the last row. So CSV and XLSX both go to a temporary file (unlinked as soon as it is open, so it is gone on every path) and the file is then streamed. Memory stays constant; the cost is disk for the length of one download. If the reviewer wants true streaming for CSV, the headers and the audit would have to lose their counts.
- **`grain` in the render token.** The plan's `RenderClaims` list has no `grain`; the page sends one (finding 2), so a PDF without it could print a different bucket than the screen. Added as an optional field.
- **`pdfSupported` and `canDownload`** are two keys on the dashboard payload (`canDownload` is D7's; `pdfSupported` is mine, the console needs to know whether to enable the PDF item).
- **403 body.** A refused download is `ApiError::PermissionDenied`, so the body reads `permission_denied: Downloads are switched off for your role.`; the assistant's tools say the bare sentence.
- **Date in the PDF's file name** is UTC (`chrono`), not the report time zone.
- **Chart default format** is applied to a numeric column that is not the tile's dimension or breakdown; a metric's saved format hint is not read by the download (the chart's own formats only).
- A small refactor so a new line fits a lint: `AppState::new` binds `clickhouse` once; `dashboard::get` is now `payload_for` + a thin handler (the print view needs the same payload).
- The public-entry count test in `policy.rs` was 8 and is 9 (renamed `exactly_nine_public_entries_exist`, reason in the test): `POST /api/render/data` is public by design.
- `/render` was added to the app frame's public prefixes (`isPublicPath`), `proxy.ts` matches it.

  - Where: `lakehouse-embed` `render_key` signs render tokens with `HMAC(EMBED_SECRET, "lakehouse/render-token/v1")`. The label is public, and the customer's server holds `EMBED_SECRET` because it signs the embed tokens.

It then reads any dashboard as that user, with that user's masking, for example an admin's unmasked data. Before this change, the same secret could read only as `Dashboard Viewer`.
  - Decision (D2 amended): render tokens are signed with a new, server-only secret, `RENDER_TOKEN_SECRET`.

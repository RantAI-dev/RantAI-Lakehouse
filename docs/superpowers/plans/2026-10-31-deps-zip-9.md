# zip 9: the upload and export code builds on the new `ZipFile::name()`

Dependabot #273 bumps `zip` from 8.6.0 to 9.1.2 in `/rust`, and CI's Rust build fails on it.
In zip 9, `ZipFile::name()` returns `Result<Cow<str>, ZipError>`, because member names are now
decoded (CP437 included) and decoding can fail. This plan replaces #273: the developer bumps
`zip` on a fresh branch from `main`, so the lockfile is regenerated against today's `main`, and
fixes the call sites. Base: `main` at `6711ad65`.

Planner: Claude Opus. Developer: a different agent (`AGENTS.md`). The developer does not change
a decision below. If the code disagrees with the plan, stop and report it.


`calamine` already brought into the tree. No crate is added, removed or re-versioned.

**Not verified**

- **The unit test T1 asks for is not written**, and no fixture was invented. Plan T1:
  "If no such name can be built with the `zip` writer, write *not tested, because …* in
  the handoff instead." No such name exists in zip 9.1.2, measured rather than assumed:
  `name()` decodes the raw member bytes as UTF-8 and otherwise as CP437, and the CP437
  table covers all 256 byte values, so `name()` cannot fail. Measured with a scratch
  program outside the repo (in `/tmp`, not committed): an archive whose 256 member names
  are the 256 byte values gives `name()` = Ok for all 256 and Err for none; and `zip`'s
  public writer API takes a member name as a `String` (`FileOptions::name` is
  `pub(crate)`), so it cannot write a non-UTF-8 name either. The `Refusal::NotZip`
  branch D2 adds is therefore reachable only by a future `zip` that can fail to decode.
- `cargo test --workspace` was not run: CI runs it on the PR (owner's rule, 2026-10-30),
  and the task scoped the local run to the commands the plan lists.

  verification block were not run: this change touches Rust only (`Cargo.lock`, one

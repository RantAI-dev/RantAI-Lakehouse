# QA round, Query Studio (P2): `QS-10`, `QS-11`, `QS-12`

Fixes for three backlog tasks from the QA round on staging (2026-11-02 to 11-12). The Execution
transparency panel shows a person without `catalog:read` the catalog's sources, marks and
freshness, says "Policy obligations: Not evaluated" for a run whose columns were masked, and
invents a source `clickhouse@lakehouse`; the asset page says a classification masks a column
(`QS-10`). Nine editor findings: starter text that is real SQL text, completion that ranks tables
above keywords, a "+" that stays enabled at 20 tabs, no search in the schema browser, a refusal

(`QS-11`). The History page: a run opens only from its SQL text, the SQL travels in the address,
the filters are not in the address, and the empty state blames the 14 days when a filter emptied
the list (`QS-12`).

`657c2502` and their anchors are corrected here. Branch: `qs-round-10-11-12`. One PR. Rust first

## 1. Decisions

- **D1. One task per commit, in the order T1 to T14.** Each commit body cites its backlog ID
  and its QA cases where the task names them. Each fix site carries a short comment with the
  ID and the case (rule 13), for example `// QS-10 (LH-QS-1-11): …`. The `QS-11` row lists nine
  cases without pairing each with its finding; where this plan names no case for a task, cite
  `QS-11` alone, never a guessed case.
- **D2. `QS-10`, catalog facts.** `POST /api/query/estimate` needs `query:read` only
  (`policy.rs:551`). A caller who does not hold `catalog:read` (`principal.has("catalog:read")`
  is false) gets the numbers of the estimate (bytes, cost, error, engine, workload) and no
  catalog facts: `sources` is `[]`, `freshnessLagSeconds` is `null`, there is no `sourceMarks`,
  and `catalogHidden` is `true`. Neither `freshness_lag` (the `system.parts` read) nor
  `certification_marks` runs for that caller. A caller who holds `catalog:read` gets the answer
  of today, with `catalogHidden: false`. The route stays at `query:read`: the run needs nothing
  from the catalog, and QS-1-AC11 says the editor still runs SQL without catalog access.
- **D3. `QS-10`, no invented source.** A ClickHouse estimate whose plan names no table answers
  `sources: []`, not `["clickhouse@lakehouse"]` (`query.rs:2841-2845`). The panel already says
  nothing false for an empty list once T5 gives it a sentence.
- **D4. `QS-10`, policy obligations are reported, not "Not evaluated".** The rewrite already
  evaluates every mask and row filter before a run and before an estimate
  (`policy_engine::rewrite_sql_for_roles`, `policy_engine.rs:336`), so "Not evaluated" is false.
  The run's answer and the estimate's answer carry `policyObligations`: a list holding
  `"Column masks"` when a table the statement reads has at least one masked column for the
  caller's roles, and `"Row filters"` when a table it reads has a row filter for them, in that
  order, each at most once; `[]` when neither applies. No table name and no column name is in
  it *(planner default, owner may change)*: the result already shows the masked values, and
  `BI-51` set the rule of not naming masked columns. A Trino run carries the list too (the
  rewrite runs for Trino). The Trino estimate keeps `policyObligations: null` (nothing is
  rewritten for it, `QS-6` decision 7).
- **D5. `QS-10`, the asset page.** The "Sensitive columns" card's description says
  `Columns a policy masks, and columns classified confidential or above. A classification alone
  does not mask a column.` *(planner default, owner may change)*.
- **D6. `QS-11`, syntax error.** A statement the parser cannot read is refused with
  `The statement could not be read: check its syntax.`, the sentence History keeps for a
  ClickHouse syntax error (`upstream_error.rs:581`), for both `PolicyEngineError::Unparseable`
  (`policy_engine.rs:166-169`) and `RewriteError::Unparseable` (`:187-189`). No mention of
  access rules or the policy engine. The sentence is a `pub const` in `upstream_error.rs` used
  by both places (rule 4: one copy of the sentence).
- **D7. `QS-11`, the starter text is a placeholder.** A new tab holds the empty string, and the
  editor shows `Write SQL here, or generate it from a question` as a CodeMirror placeholder
  (grey, not part of the text). A stored tab whose SQL is exactly the old starter text
  `-- Write SQL here, or generate it from a question` is read as `""`; any other text is kept
  as it is.
- **D8. `QS-11`, completion ranking.** Outside a `FROM`/`JOIN` position and outside a qualifier
  (`o.`), tables and columns are offered without a boost over the keywords, so a keyword that
  matches what was typed ranks by CodeMirror's own match score. After `FROM`/`JOIN` tables keep
  `TABLE_BOOST`; after a qualifier columns keep `COLUMN_BOOST`; the `{{` list and the messages
  are unchanged. The QA report that a click on the keyword `select` inserted a table is not
  explained by the code: T7 reproduces it first (see T7).
- **D9. `QS-11`, the tab limit and the statement limit.** At 20 tabs the "+" button is
  disabled and the sentence `At most 20 query tabs are kept. Close a tab to open another.` is
  shown beside it as text, as #453 and `BI-54` did for their limits (QA-1: "Opening a 21st query
  tab is refused, with a message that at most 20 tabs can be open"). The refusal of more than 20
  statements is shown as text under the Run button, `role="alert"`, and stays until the open
  tab's SQL changes or another tab is opened: `At most 20 statements are run at once. Split the
  buffer into smaller queries and run them one after another.` (the toast's own two lines). No
  toast for either *(planner default, owner may change: the placement)*.
- **D10. `QS-11`, schema browser search.** A text field `Search tables` at the top of the
  browser filters the listed tables by a case-insensitive "contains" on the table's label and
  its reference. A layer with no match is not drawn. With no match at all:
  `No table matches "<text>".` The filter is not stored.
- **D11. `QS-11`, Fix with AI.** "Fix with AI" is shown only when the failed statement's error
  code is `invalid_request` (the server's 400 or 422: something in the statement). A permission
  refusal, a hidden table (404), an outage or a rate limit get no button: changing the SQL does
  not help, and the decision (`query-studio-editor.md` decision 13) offers it on "a failed
  statement".
- **D12. `QS-11`, the result summary.** "Rows" says the rows shown, `result.rows.length`, and
  when the result was cut it reads `<n> shown`. `rowCount` keeps its meaning on the server (the
  rows the engine sent before the route's cut; `tests/query_result_cap.rs:234-262` pins it),
  and the console stops showing it.
- **D13. `QS-11`, the side panel label.** The History side panel shows a `blocked` run as
  `Refused`, as the History page does (`query-history-page.tsx:263`). This is the rest of
  `LH-QS-4-02` (`query-history.md`, Exceptions).
- **D14. `QS-11`, statistics.** Minimum and Maximum are cut with an ellipsis inside their own
  cell, and the full value is the cell's `title`.
- **D15. `QS-12`, a run opens by its id.** History links to `/query-studio?run=<id>`. Query
  Studio asks the server for that run with `GET /api/query/history?id=<id>` (the caller's own
  runs of the last 14 days only, the same owner scope and window as the list) and opens its SQL
  in a new tab on its engine. A run it cannot find answers
  `This run is not in your history of the last 14 days.` where the saved-query link's error is
  shown, and no tab is opened. `?sql=` stays for the catalog's "Open in Query Studio" links,
  which carry a starter query, not a person's SQL.
- **D16. `QS-12`, the row.** The whole row opens the run (pointer cursor; a click that ends a
  text selection does not navigate), and the SQL text stays the keyboard-reachable link,
  styled as a link (`text-primary`, underline on hover) *(planner default, owner may change)*.
- **D17. `QS-12`, the filters are in the address.** The page reads `status`, `engine`,
  `minDurationMs`, `table`, `from`, `to` (each `YYYY-MM-DD`) and `page` from the address when it
  opens, and writes them back with `window.history.replaceState` on every change, so the back
  button is not filled with one entry per keystroke. A value the page does not know (a status
  outside the four, a date that is not `YYYY-MM-DD`, a page below 1) is ignored. Read from
  `window.location`, as `use-query-studio.ts` does, to avoid a `useSearchParams` Suspense
  boundary.
- **D18. `QS-12`, the empty state.** With a filter set: title `No runs match these filters`,
  description `Clear a filter and try again.`, and the action is "Clear filters". With none:
  as today.
- **D19. No assistant change.** None of this is a dashboard behaviour, so the assistant-parity
  rule asks for nothing, and `tests/fixtures/tool_schemas.json` is not regenerated. `run_sql`
  keeps its reduced shape (`compact_query_result`, `routes/ai/tools/data.rs:185-215`), which
  does not carry `policyObligations`; `run_saved_query` returns the run's whole body, so it
  gains the field, with no schema change.
- **D20. Reuse, no new helper where one exists** (rule 4): `Principal::has`,
  `is_valid_history_id` (`query.rs:3537`), the `?saved=` handoff pattern
  (`use-query-studio.ts:1407-1474`), `historyQueryString` (`src/lib/history-query-params.ts`),
  `queryService.listHistoryPage`, `queryEngineLabel`, `MAX_QUERY_TABS`,
  `MAX_STATEMENTS_PER_RUN`.

## T1 `SEC-38`: the signing keys' address comes from the provider's discovery document

- **Today.** `A/state.rs:587-604` `oidc_config` sets `jwks_url` to
  `OIDC_JWKS_URL`, else `{issuer}/.well-known/jwks.json`. Entra ID and
  Google serve neither at that path, so every token fails unless an
  administrator finds and sets `OIDC_JWKS_URL` by hand. `U/oidc.rs:200-300`
  `JwksClient` fetches and caches the key set.
- **Decisions (planner).**
  1. `OIDC_JWKS_URL` set: used as today (an explicit setting wins).
  2. Unset: the address is `jwks_uri` from
     `{issuer}/.well-known/openid-configuration` (OpenID Connect Discovery
     1.0 section 4). It is read lazily, on the first key lookup, not at
     start-up, so an unreachable provider does not stop the API (the same
     stance as the key set today); it is cached with the key set's TTL and
     read again when a `kid` is unknown, the same refresh rule.
  3. The discovery document is trusted only if its `issuer` equals the
     configured issuer exactly (Discovery section 4.3), and `jwks_uri` is an
     absolute `https` URL (`http` only when the issuer itself is `http`,
     for a local test provider). Anything else is a fixed `AuthError`, the
     provider's text never reaches a response (principle 4), and the log
     says which check failed.
  4. The issuer is administrator configuration, not request input, so the
     connector address allowlist does not apply (as `U/openfga.rs:38` notes
     for its own calls); say so in the comment.
  5. Docs: `.env.example` and `docs/OPERATIONS.md` (single sign-on) say
     `OIDC_JWKS_URL` is optional and when to set it; `config.rs:431` doc
     updated.
- **Check.** wiremock tests: discovery then keys, a token verifies; an
  `issuer` mismatch is refused; an `http` `jwks_uri` under an `https` issuer
  is refused; `OIDC_JWKS_URL` set skips discovery (no discovery request is
  made); an unknown `kid` re-reads. The existing test at
  `A/routes/auth.rs:1468` keeps passing (adapt only its setup if it relied
  on the default path, and say so). Each new test fails without the change.

## T2 `SEC-39`: a group overage is said, not silent

- **Today.** `U/oidc.rs:356` reads the groups claim; an Entra ID token for a
  user in more groups than fit carries `_claim_names: {"groups": …}` and
  `_claim_sources` instead of `groups`, so `mapped_role_names`
  (`U/oidc.rs:661`) maps nothing and the user signs in with no mapped role,
  silently.
- **Decisions (planner).**
  1. Detect the overage marker for the configured groups claim
     (`_claim_names` has a key equal to `groups_claim`).
  2. Sign-in still succeeds with what it has (no mapped role): refusing
     would lock out a user who also holds roles granted in the console.
  3. It is logged at `warn` with the user's id and provider, never the token
     or the claim source URL.
  4. The user is told: the sign-in response (and the console's sign-in
     page, wherever it shows the result of the OIDC callback today) carries
     a fixed notice: "Your account is in more groups than the sign-in token
     can list, so no group-based role was applied. Ask an administrator to
     assign your role directly or to limit the groups sent in the token."
     Find the callback route and the console page; one notice field, one
     place it is shown.
  5. Following the Microsoft Graph link (the full fix) is out of scope:
     add it to the backlog row's text as the remaining part, not a new ID.
- **Check.** Unit test: claims with the marker are detected, claims with
  `groups` are not; route test: the callback's response carries the notice;
  console test for the notice. Each fails without the change.

  keys) instead of one; the rate is bounded the same way as before (one
  refetch per unseen `kid`). Not a finding; noted for `SEC-40`.

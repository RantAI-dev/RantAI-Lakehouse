## Problem

`POST /api/identity/users` (Administration → Users → **Invite User**) created
an account with roles and tenants but **no credential**. The only local
password in the product was the bootstrap admin's. Every invited user could
therefore sign in **only** through single sign-on.

- A site without an identity provider — staging, the first customers — could
  not give an account to anybody but the bootstrap admin.
- There was no way to reset a lost password either.

## What the user can do when this is done

1. An administrator invites a user, and the console shows a **temporary
   password** once, in a dialog, with a Copy button.
2. The temporary password is generated by the server. The administrator never
   chooses it, and the person signing in never chooses it.
3. The new user signs in with the temporary password and is **forced to change
   it** at the first sign-in; every other page is refused until they do.
4. The temporary password is shown **once**. It cannot be shown again, because
   the server keeps only the hash of it — and it is never logged, never
   audited, and never listed.
5. An administrator can **reset** a user's password from the users list. The
   reset hands out a new temporary password, shown once the same way, and
   **ends every session that user holds**.
6. A reset cannot be used to take over somebody else's account: only an
   administrator who holds every permission may reset the password of a user
   who holds every permission. Anyone else is told the user does not exist.
7. Nobody may reset their own password that way; a user changes their own
   password with the change-password form, which asks for the old one first.

## Not included

- **Emailing the password.** There is no mail delivery: the administrator
  hands the temporary password over, in person or over a channel they trust.
- **Self-service "forgot password".** A user who loses their password asks
  an administrator to reset it.
- **Editing or deactivating a user's roles.** That is a separate item. The
  reset sets a password; it does not change what the user may do.
- **The assistant.** See below.

## Asking the assistant

No. Creating accounts and resetting credentials are administrative acts on
other people's access; the assistant is not given a tool that hands out
passwords. The assistant's own dashboard work (`AI-15`) is unrelated to the
identity directory.

## Decisions

The planner's decisions (plan D1–D7, 2026-11-02). The product owner was
informed; none is signed yet, so the defaults below are the ones in force.

| # | Decision | Default | Signed |
| --- | --- | --- | --- |
| 1 | How long the temporary password is, and over which characters | 24 characters from a 59-character alphabet with no look-alike characters (`0`/`O`, `1`/`l`/`I`, `L`/`l` all excluded), about 142 bits | |
| 2 | Where the temporary password comes from | The server, from the operating system's random source. The caller never chooses it | |
| 3 | Where the temporary password is shown | Once, on the invite and on the reset, in a dialog with a Copy button. Never stored in clear, never logged, never audited, never listed | |
| 4 | Whether an invited user must change the password | Yes, at the first sign-in, exactly like the bootstrap admin | |
| 5 | Who may reset a password | Any administrator with `identity:write` — but only an administrator holding every permission (`*:*`) may reset a user who holds every permission. Anyone else gets the same "not found" answer as for a user who does not exist | |
| 6 | Whether a reset ends the user's sessions | Yes, every live session of that user, including the one they were using | |
| 7 | Whether single sign-on changes | No. An SSO user may also be given a password; that is an administrator's choice, not a change to SSO | |

## Limits to tell a customer

- The temporary password is shown **once**. If it is lost, it cannot be
  recovered — it has to be reset, which ends the user's sessions.
- The console does not email the password. Somebody has to hand it over.
- A reset ends every session of that user. Work in progress in the console is
  lost when their sessions end.
- A user with a temporary password can reach nothing but the change-password
  screen until they change it.
- There is no "deactivate this account" button yet, so removing someone's
  access means resetting their password (which invalidates it and ends their
  sessions) and changing what they may do by other means.

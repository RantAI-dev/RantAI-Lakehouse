## Why

A question about a particular table in the chat needed the person to name
it in words. A table's own page told the chat only that the person was in
the Catalog, so "describe this dataset's columns" there named no particular
table.

## Decisions

1. **The picker (Owner, 2026-11-27).** Typing `@` in the composer opens a
   search over the tables `GET /api/catalog` lists for the person, which
   needs `catalog:read`. A picked table becomes a chip in the message. When
   that route answers `supported: false` (a tenant refusal), the picker says
   so and offers nothing. A person with only a per-table `query:read` grant
   gets no picker; the server still checks any mention they send.
   A mention covers Silver and Gold tables; Bronze tables are not in the data
   map, so the picker does not offer them.
2. **At most 5 mentions per message (Owner, 2026-11-27).** The composer
   stops at 5 and refuses a 6th. The server takes the first 5 and silently
   ignores the rest.
3. **The asset page sends its table as page context (Owner, 2026-11-27).**
   A table's own page (`/data/assets/<id>`) calls `setPageContext` with its
   table, the way the dashboard page sends its board.
4. **What a mention adds (Owner, 2026-11-27).** The chat body gets an
   optional `mentions: [{ kind: "table", key }]` with `#[serde(default)]`.
   The server checks each key with the catalog's own reach helpers
   (`ensure_key_in_reach` / `ensure_asset_readable`), never a second reach
   check. A mention that fails is dropped with no trace in the answer; the
   same 404 as an unknown key keeps it from being an oracle. Survivors are
   rendered as one block in the page-context line: the table's name plus its
   described columns from the data map. All page context stays within the
   existing 6,000-character cap (`PAGE_CONTEXT_MAX_CHARS`), cut last-first
   if over. There is no new tool and no prompt text.

## What users get

Ask about a table by pointing at it, and get that table's name and columns
in the answer. On a table's page the chat already knows which table is open.

> @orders what columns does it have?

## Target specs

"Today" is what the code did before this change, read from the code, not
tested. A target is either a decision the owner signed on 2026-11-27 or
marked *(proposed)*: the planner's number, which the product owner confirms
or changes on the feature page before the plan is written.

| Capability | Today | Target |
| --- | --- | --- |
| Naming a table in the chat | The person types its name; the chat has no field for it | `@` in the composer opens a search over the tables `GET /api/catalog` lists for the person (`catalog:read`); a picked table becomes a chip in the message |
| Mentions per message | None | At most 5. The composer refuses a 6th; the server takes the first 5 and ignores the rest silently |
| A tenant refusal in the picker | n/a | When the route answers `supported: false`, the picker says so and offers nothing |
| A table page's context | "the Catalog" | The table's own page sends its table through `setPageContext`, as the dashboard page sends its board |
| What a mention adds | Nothing | One block in the page-context line: the table's name plus its described columns from the data map, within the existing 6,000-character cap, cut last-first if over |
| Reach of a mention | Nothing | Each key checked with the catalog's own helpers; a failure dropped with no trace, using the same 404 as an unknown key so a mention is not an oracle |
| Assistant surface | No tool for this | No new tool and no prompt text |
| A person with only a per-table `query:read` grant | No picker | No picker, because the picker needs `catalog:read`; the server still checks any mention they send and adds nothing from a table they may not read |

For every capability: The assistant uses the same API and permissions as the user; anything that deletes, shares or publishes asks for approval first.

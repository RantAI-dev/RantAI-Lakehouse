## Why

A customer who wants dashboards, ad hoc SQL and the assistant over their
own database should not have to copy that data into a lakehouse first. The
product owner decided on 2026-11-11 that the source is read through **one**
query engine chosen for the installation, and that the two engines never
run side by side for this, so they do not compete for the host's memory.
This is part of making the product installable in parts.

## What users get

An operator installs the console, the API and one query engine. Dashboards,
Query Studio and the assistant read the customer's own tables in place;
nothing is copied into warehouse storage. The console says which mode and
engine are active, and reports services that were never installed as
"unknown", not as broken.

### Source coverage matrix

External sources are read, never copied. Both engines go through the
product's read-only guard and governance rewrite; the matrix is what each
engine can reach, not a promise that an unregistered source works.

| Engine | Sources in scope | Mechanism |
| --- | --- | --- |
| ClickHouse | PostgreSQL, MySQL, remote ClickHouse | ClickHouse external table engines over operator-supplied connection settings |
| Trino | PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, ClickHouse, Snowflake, BigQuery, Redshift | Federated catalogs, operator-supplied catalog properties mounted read-only |

Anything outside this matrix answers "unsupported" with an honest sentence
(`AGENTS.md` principle 2), never a fabricated success or a silent fallback
to the other engine.

## Installation modes and mutual exclusion

`LAKEHOUSE_INSTALL_MODE` is `full` (default) or `bi-only`, and
`LAKEHOUSE_QUERY_ENGINE` is `clickhouse` (default) or `trino`. Both are
trimmed and case-insensitive; an empty value means unset; any other
non-empty value is a `ConfigError` that stops start-up. Fail closed is the
only honest posture: a typo must not quietly leave data being copied, or
start a second engine.

In `full` mode both variables keep their pre-`BI-44` behaviour: existing
configs and deployments are unchanged, including one that names both
engine URLs. In `bi-only` mode:

- with `clickhouse`, `TRINO_URL` must not be explicitly set (non-empty);
- with `trino`, `TRINO_URL` must be explicitly set and `CH_URL` must not be.

The two rules are one invariant: exactly one engine service exists, and it
is the chosen one. `Config::engine_allowed` is the one place callers ask
whether a named engine may be used; unknown names are refused in `bi-only`
mode so a typo cannot fall through to the full stack's ClickHouse default.

## Governance enforcement model

A read travels the same choke point whether its table is local or external:

1. `POST /api/query/run` and `/api/query/estimate` resolve the engine
   (`Config::default_query_engine_name` when the request omits it) and
   refuse the inactive engine before parameter substitution.
2. The read-only guard checks the statement with that engine's rules;
   `Trino` additionally refuses write, session and procedure keywords.
3. `rewrite_sql_for_principal` uses `sql_rewrite::Engine::Trino` or
   `Engine::ClickHouse` from the resolved name, so the policy engine's
   table substitution applies the principal's masks and row filters in
   that engine's dialect. `sql_rewrite` masks through a derived table,
   never an expression left clear in a projection.
4. An unparseable statement, an unenforceable authored condition or an
   unsupported construct refuses the request. There is no "no policy
   matched, so allow everything" path.

Slice 2 extends the same model to registered external schemas and tables;
slice 1 proves the resolved engine is the one the rewrite and dispatch
both use.

## Security posture

- **Read-only guard.** Every ad hoc statement must pass `is_read_only`
  (and, for `Trino`, `is_trino_safe`) before a rewrite prefetch or engine
  dial happens.
- **SSRF / internal hosts.** Operator-set engine addresses are deployment
  configuration, never request input. Connector-probe targets go through
  `connector_probe::resolve_checked`: internal ranges are blocked unless
  the operator opts in, redirects are not followed, and dials are bounded.
  The console cannot name an internal host for a connector test by default.
- **Credential at rest.** External-source credentials are references
  (`env:` / `file:`) resolved by `connector_secret_store` and the
  allowlisted resolver; values live in `SecretValue`, are sealed at rest,
  and are never returned by a read route. `SECRET_MANAGER` stays optional.
  No default credential is baked into either standalone Compose file;
  must-set variables use `${X:?}`.
- **No upstream error leakage.** Engine and store errors are classified
  (`upstream_error`, `classify_sqlx_error`) into fixed sentences and a
  reference id; the raw text goes to the log, never to a response, health
  row or history record (SEC-11 and its route guard).
- **One engine, one process.** The standalone files do not publish the
  federated coordinator on the host, and do not deploy the warehouse
  services; the API's mutual-exclusion check is the second line of defence.

## Resource and memory budget rationale

The owner's reason for one engine is host memory: two coordinators on the
same machine compete for RAM even when only one is in use. Slice 1 removes
the second engine and the warehouse services from the installation files,
so the baseline cost is the application database, one engine, the API, the
console and a bounded (1 GiB) PDF renderer. No peak figure is claimed here:
a budget needs a dated, version-pinned measurement in `docs/plans/`, which
slice 4's acceptance gate supplies. Until then the target is the
*(proposed)* structural fact — one engine process — and the numbers stay
unmeasured rather than assumed.

## Acceptance checklist

Run by the product owner on a running installation. A step not performed
is never a pass.

- `BI-44-AC1` A fresh install keeps `full` / `clickhouse` behaviour; a bad
  mode or engine value stops the API at start with a message naming the
  variable, and a `bi-only` config naming both engines is refused.
- `BI-44-AC2` Query Studio with no engine selected runs on the configured
  engine; an explicit request for the other engine gets a 400 naming the
  configured engine and no dial to the other one.
- `BI-44-AC3` A masked column and a row filter still apply to a query over
  an external table, in the active engine's dialect; unparseable SQL is
  refused, not run.
- `BI-44-AC4` The Services view and readiness report only the chosen
  engine as checked; warehouse-only services and the other engine read as
  unknown/skipped, never as failed.
- `BI-44-AC5` `GET /api/settings/deployment` reports `installMode` and
  `queryEngine`, and the console shows them without guessing from probes.
- `BI-44-AC6` The two standalone files start only the seven named services
  with exact pinned images from the root file; their static suite and the
  image-digest lint pass.
- `BI-44-AC7` *(proposed)* A `bi-only` installation runs one engine process
  and no warehouse services; peak RSS is measured against `full` in slice
  4 and recorded in a `*-RESULT.md` before any number is stated as fact.

## Not included

- Copying source data anywhere (the point of the feature).
- External catalog registration, credential forms and schema introspection
  (slice 2).
- Dashboard tiles, saved SQL sources and the assistant tools running over
  the active engine (slice 3), plus console UX, `lakehousectl --mode
  bi-only --engine ...` and the end-to-end gate (slice 4).
- Changing the root `docker-compose.yml` default stack.

## Asking the assistant

Assistant parity is part of this feature (`AGENTS.md`): slice 3 names the
tool schemas, the dashboard page context and the standard request set
(`AI-15`) that let the assistant use an in-place source through the active
engine. Until then the assistant may only use local warehouse tables; the
installation mode is reported truthfully and no external source is
advertised to the model.
